### Unreleased (cleanup round, 2026-11-06)

- **New: the wallpaper-properties panel can import this wallpaper's current values from WE (read-only, #341).** Scene wallpapers ship author defaults (`project.json`'s `general.properties`) that often switch every feature component on, while the user may have turned some off in WE — until now the plugin only knew the author defaults plus its own `userProps` overrides and could not read `<profile>.wproperties.<wallpaper path>.MonitorN.*` from the WE install root's `config.json` (the user's live values). `GET /props/<token>` now also carries a read-only `we` field (`{ ok, values, monitor, profile }`, never merged into defaults/overrides), and the panel shows an "Import from WE (N)" button: values are coerced per control type (bools accept `true/false/1/0` strings, sliders become numbers, colour/text controls only accept strings), only entries that differ from the default are written to `settings.userProps`, and same-as-default ones are left out; the button disappears once there is nothing left to import and can come back if WE changes again. Reads are strictly **read-only** (WE files are never written) and degrade gracefully: missing `config.json`, malformed JSON, multiple profiles, multiple monitors, and path case/separator mismatches all return `{ ok:false, reason }` instead of throwing; the install root is found by trying `DSH_WE_STEAM_ROOT`, the `steamapps` directory on the same drive, other libraries from `libraryfolders.vdf`, and the parent of a `projects` directory — no hard-coded path, so WE living in a SteamLibrary on another drive still works. **Also fixes a silent divergence**: entries with `editable: false` used to be dropped entirely, whereas WE's semantics are "hidden in the panel, still delivered" — they now stay in the payload with `hidden: true` (filtered by the panel, still seeded). Guards: `verify-steam-discovery` gains section G (path normalisation / vdf unescaping / flat and per-profile shapes / monitor selection / case and suffix tolerance / negative controls / candidate ordering / end-to-end including the cache and "reads do not write files"); `verify-scene-live` C5 now asserts `internal.hidden` and that hidden values still reach the seed; `verify-picker-props` gains a "read-only import from WE" section (hidden rows not drawn, button count, import persists with type coercion, button disappears afterwards, negative control). Host-side plus client-side only.
- **Fix: the inventory cold scan that made startup slower on large libraries (#158).** The plugin used to fire its `/inventory` prefetch during activation (the first block of `apply`), and on a large library (2,600 projects / 13,941 files) that cold call waits for a full disk scan (measured end-to-end latency 1.6–2.0 s) — it competed with the host's own startup for I/O, yet **no UI** was waiting for the list before the first paint. The inventory leg now runs after the startup chain (settings → fontset) through `afterFirstPaint()`: two rAFs make sure a frame has been presented, then `requestIdleCallback` (1 s fallback), and hosts/test harnesses without browser APIs pass straight through, keeping the previous behaviour. The fontset-list prefetch stays at the `apply` entry (it is cheap and genuinely saves one serial round trip). **`immediately` is untouched**: the host's `ClientEntries.start()` runs `create` + `loader.await()` for every plugin, so dropping it would only start the download later (see correction ① in `ISSUE-AUDIT-148PLUS.md`) — the "must wait for the plugin to load before a new session" half is upstream and cannot be fixed in this repository. Guards: the ordering checks in `fontset-load-smoke` now assert "fontset list before settings, inventory after settings"; `verify-client` / `live-frame-backfill-smoke` / `verify` all green.

- **Fix: "Sidebar fully transparent" cleared the panel but not the blur on the decorative plates (#329).** Since 1.4.2 the sidebar blur lives on the decorative plates rather than the panel: the panel itself is clean (`background-color: rgba(0,0,0,0)`, `backdrop-filter: none`, `--we-readability-floor: 0`), yet `[data-we-surface-plate="right-sidebar"]` still paints `blur(7px) saturate(1.3) brightness(1.04) contrast(1.01)`, so the wallpaper stays blurred. The plates hang under `body > [data-we-surface-root]`, outside the panel subtree, so the full-clear group that zeroes seven variables on the container cannot reach them — they read `--we-sidebar-blur` / `--we-sidebar-saturate` / `--we-glass-brightness`, which do not intersect that zeroed set; and with "sidebar glass follows global" the sidebar blur is overridden by the global blur, so it cannot be zeroed separately. The fix turns `backdrop-filter` off on both plates when the switch is on (wallpaper gate + full-clear gate + `data-we-glass-page` + the respective `data-we-left-sidebar` / `data-we-sidebar-glass` gate), and the switch hint / tooltip plus both i18n entries now say blur is included. Guards: `verify-readability` F7 gains F7h (both plates in one rule, both `none !important` prefixes present) and negative control F7-5 (missing wallpaper gate / missing full-clear gate / only the `-webkit-` prefix must all be caught). Pure CSS plus copy — takes effect on refresh.

- **Fix: the sidebar-corner controls — the four buttons now share one width, the per-corner toggle's solid fill means "round" again, and the two bulk buttons are gone.** The two segmented rows on the settings page used `grid-auto-columns: 1fr`, whose min-content floor made each column follow its own label width ("Follow native" vs "Large 20px", much wider in English). The settings page now adds `.we-picker__seg--corners-eq` (`grid-auto-columns: minmax(max-content, 1fr)`), so all four columns take the widest label and neither language is clipped; the sidebar pane (`surface === "sidebar"`) omits it and keeps content-width columns for the narrow shell. Guards: `verify-client` / `verify-scene-live` (756, label sequence unchanged) / `verify-i18n` (zero orphan keys) / `verify:docs` / `verify-static` all green.
- **Fix the scene wallpaper placeholder (#317).** The fullscreen placeholder and the static-frame fallback use the author's original preview image (`/preview/<token>?full=1`), while the library cards keep the thumbnail; the preview query string is built through `URL`, so a preview that already carries a query never gets a second `?` (the old form made the server miss `full=1` and the fullscreen placeholder fell back to the thumbnail). Two layers stacked into it: ① the main package's `src/client.js` official-mode drag path fires `petLink.performer.onPull()` on **every `pointermove`** (deliberately — the drawer's follow-the-finger preview depends on it), and ② the `performer` facade in `packages/pet-link/src/pet-link.js` **always dispatched to the linked provider** regardless of the current mode; linked's `run()` then took its `det.mode !== 'linked'` branch (no `dsh-pet-dshwe` runtime installed / link switch off — the common case for nearly everyone) which calls `rt.fallback()`, wired in production straight to `wallSidebarToggle()`. So "drag = one mascot click per frame": a 40-frame drag reproduced **30** sidebar open/close toggles on a real machine — the right sidebar visibly flickered. Fixed at two layers (deliberate defence in depth; either one alone can be re-ignited by the next change):
  — **the facade routes by provider**: `performer.onGrab / onPull / onRelease / snapshot` now go through `active()`, and the native performer is already a quiet no-op (`Promise.resolve(false)`), leaving the main package's native drag path completely untouched;
  — **gesture segments never fall back**: in the degraded branch of `run(logic, gesture)`, `gesture === true` returns `fallback: false` outright. This one covers the TOCTOU window — the facade probes as linked, then by the time the provider re-probes the target is gone (mascot hidden mid-drag / runtime dropped), and that degraded branch used to toggle the sidebar once in the middle of the drag. Non-gesture fallback semantics (a tap routing into `run`) are unchanged.
  After the fix, an end-to-end repro (real `src/client.js` drag segment + the real pet-link assembly) shows `toggles=0` for the whole drag and exactly one open/close commit on release, identically in linked and native modes.
  Guards: `test/verify-pet-linked.mjs` gains 3b (native-mode gestures never fall back; taps still do), 3c (the facade routes by current provider, discriminated by **return value** — native always `false` / linked resolves `true`, with a linked control case so "always false" can't pass), and 3d (the mid-drag probe-flip TOCTOU window); `test/verify-pet-rope-entry.mjs` gains "official-mode drag forwards gestures per frame but synthesizes no sidebar toggle" — pinning the "one onPull per frame" shape that **must** stay, while pinning "at most one open/close commit per drag". Each guard was negative-controlled (facade only / gesture-only / both reverted) and turned red as expected.

### v1.4.0 (2026-10-22 · published to npm)

> The first release shipped as a **complete eight-package release set**: the main package and its
> seven subpackages share one version and go up together, and the main manifest pins each child to an
> **exact version** — so installing the single name `dsh-plugin-wallpaper-engine` pulls all eight.
> `package.json` `version` `1.3.3` → `1.4.0` (minor: the first official release after the package split).
> **The host half changed ⇒ restart `dsh web` after upgrading; client-only parts just need a page refresh.**

#### The eight-package release set goes to npm for the first time (2026-10-22)

- **`dsh-plugin-wallpaper-engine` plus its seven subpackages ship together at `1.4.0`** — the first release where "one package name installs all eight" is actually true on npm (1.3.3 and earlier published the main package only; the subpackages existed in the source tree alone). Install with `dsh plugin --profile <p> add dsh-plugin-wallpaper-engine` or `npm i dsh-plugin-wallpaper-engine`; the seven children resolve as **exact-version** runtime dependencies, so nobody installs them by hand.
- **The order cannot be flipped**: the seven children first, the main package last. Shipping the main package while a child is missing makes a user's install fail **on their own machine** with `ERR_PNPM_FETCH_404 … installing the dependencies of dsh-plugin-wallpaper-engine@1.4.0` and roll back entirely (measured). The release loop follows `release-set.json`'s `publishOrder` and stops at the first failure.
- **A GitHub Release must carry all eight tarballs plus `release-set.json`**; a main-only tgz is a package nobody can install. Offline installs go through `npm run install:release -- --set <dir> --profile <name> --dsh-home <dir> --app-closed`, which pins the seven children to the sibling tarballs via profile `overrides`.
- A new hard guard, `test/verify-release-set.mjs`, packs the set for real and inspects the eight tarballs' bytes: the main manifest must pin all seven children to their exact versions, the main tarball must carry no development directories, and every subpackage tarball must contain the browser half its own `exports['./client']` points at. The procedure lives in [`CONTRIBUTING.md`](../../CONTRIBUTING.md).

#### Presets carry a light/dark preference + fresh installs default to "dark + Author's preset" (2026-10-22)

- **A fresh install now starts with the look the author uses daily**: on first installation (no host save file **and** no local save in the browser) the plugin applies the "Author's preset" and switches the theme to dark. Upgrading users — and users whose host save file was deleted while the browser copy survived — are unaffected. No sentinel key: applying writes the save, so the next start takes the host branch and this path can only fire once. Failures stay silent (a brand-new user should not meet a red error line); the diagnostic line remains for troubleshooting. The theme leg also waits for its service: the host `theme` service is not available early in startup, so the theme layer re-writes the preference once it is ready (idempotent).
- **Presets gained an `assets.theme` section (`{"preference":"dark"|"light"}`)**: applying a preset sends the preference to the host `theme` service — the only section written outside the plugin. It shares the service handle with "theme follows wallpaper" but does **not** touch that feature's yield bookkeeping, so leaving a wallpaper never puts the user's just-applied theme back. Only "Author's preset" declares `dark`; the other six carry nothing (absent = leave the theme alone). The sanitizer accepts only `dark` / `light` and never guesses `auto` / `system` (a wrong guess would be a silent no-op).
- **Retired the "try the Author's preset" intro dialog**: the component, both mount points, the localStorage sentinel, its CSS, its English word-list entries and its browser guard are gone; the guards were rewritten as first-install + theme-leg checks (guard chain verify 92→91, all 105→104).
- **Fixed a silently dropped section** (reported from the user's own machine: applying Author's preset in light mode did not turn the UI dark). The host's `publicAssets()` is a **whitelist** that only passed font / mascot / avatar, so the new `assets.theme` section never reached the client; the theme leg saw no section, skipped silently and reported nothing. The section is now echoed back as-is, with two guards: a source-level one (the `publicAssets` body must contain an `out.theme` branch) and an end-to-end one (a real `GET /glass-presets/factory-author` must return `assets.theme.preference = "dark"`) — the latter watches exactly the seam between "the branch exists in source" and "a request really receives it". Both were mutation-checked. `verify-presets` 226 → 227 checks.
- **Known bounds (left for a later decision)**: the `export` path rebuilds its asset section from `ASSET_SEGMENTS` (font / mascot / avatar) and therefore **does not carry `theme`**, so export → import loses the preference (GET / list / create / import all keep it); the first-install flush value is hard-coded to `dark`, consistent with what Author's preset declares today but a second source of truth. The host half (`lib/routes/presets.js`) changed too ⇒ **restart `dsh web`** for the full effect (refreshing the page is not enough).
