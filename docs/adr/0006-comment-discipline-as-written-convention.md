# ADR-0006: 注释与文档纪律改为纯写作约定，撤除文档类机器守卫（Comment discipline as a written convention）

- **Date**: 2026-09-30
- **Status**: Accepted
- **Deciders**: YV3507
- **Implementation**: 纪律条文与 ADR 已落地；**文档类守卫文件已物理下线**
  （`verify-comment-discipline` / `verify-ledger` 已从 `test/` 删除、并移出 `npm run verify:docs` 链；
  详见 [ADR-0007](./0007-machine-checks-target-code-not-prose.md) 的撤除清单）
- **Amends**: [ADR-0004](./0004-two-tier-guard-verification.md)（软档内的**文档类**守卫被撤除；分档本身不变）

> 纪律条文本身住在 `docs/README.md` §写作纪律；本文记**为什么用约定而不是守卫**。

## Context

本仓此前的"代码即文档"是靠**机器守卫**钉住的：把若干条写作纪律写成 `test/verify-*.mjs` 的断言，
例如"注释里不得出现日期"、"不得出现叙事回溯词"、"常青文档不得引用本机专用路径"、
"文档里的计数必须等于构建清单条数"等。这些守卫确实**起了作用**——
实测证据是：被守卫覆盖的数字没有漂（构建清单计数、路由条数、工具清单），
而**没被覆盖的数字全漂了**（内联模块计数在两份文档里各写一个值且互相矛盾、
路由条数所在文档与生成物不一致、滑条计数与实现不符）。

但这条路线有三个**结构性**代价，随着文档面增长越来越重：

1. **守卫在替作者思考**。写作纪律是"这句该不该留"的判断。把它降级成正则匹配之后，
   作者关心的是"别踩词表"，而不是"读者读到这句话会不会被误导"。词表还没法覆盖真实判断
   —— 它只能抓字面，抓不住"这句在断言一个已经不成立的事实"。
2. **纪律的守卫本身需要维护，且会腐化**。守"计数必须现算"的守卫要能**找到那两句散文**
   并复算；于是改写句子会让判据**静默失效**，守卫转而去守"句子别被改写"。
   本仓实际出现过守卫**内部自相矛盾**（正文写一个数、自己的规则行写另一个数，两个都对不上）。
3. **摩擦落在最不该付的人身上**。一次文档排版改动与一次发布面缺陷此前共用同一种红
   （见 ADR-0004），代价是把文档改动与高风险改动捆在一起。

同时，**真正防住腐化的机制其实不是"守文档"，而是"别把会漂的东西放进文档"**。
本仓已经有一条这样的既有惯例，写在 `README.md` 里：
> 每个控件的取值范围与默认值**直接看控件本身**。

把这条惯例贯彻到底，比给它配一条正则守卫更根本。

## Decision

**注释与文档纪律改为纯写作约定，不再配文档类机器守卫。** 具体：

- **D1 —— 撤除文档类软档守卫**：断言"注释措辞"与"文档散文"的那些守卫下线，
  从 `npm run verify:docs` 的链条里移除。**注意边界**：只撤"文档/注释/账本散文"类；
  守**代码**问题的守卫（可达性、退役线、声明孤儿、模块布局）**保留**——
  它们守的是死码与越界，不是措辞。
- **D2 —— 常青文档不写会漂的数值**。判定标准是"这个数字会不会随代码变"：
  设置默认值与范围、枚举清单、条数、行数、体积、耗时阈值 —— 一律改为
  **符号引用**（指向唯一真源）或**复算命令**。真源的位置：
  设置 → `lib/settings-schema.js`；路由 → `docs/ROUTE-INDEX.md`（生成物）；
  各类计数 → 其生成器或构建清单。
- **D3 —— 机制、不变量、契约写在代码旁边的文件头**，文档只留决策、顺序、验收判据与证据锚点。
  这条不是新增纪律，是把既有的写成明文。
- **D4 —— "实测 X ≈ Y"这类出处**：留在**它被实测的那个代码位置**附近（守卫或实现旁），
  不搬进常青文档的散文 —— 搬进文档就是把一个会漂的数字放进无人复算的地方。
- **D5 —— ADR 里的 `Date` 例外**：日期是账本性质、不描述现状，保留。
  腐化的定义是"**断言现状却会漂**"，不是"出现数字"。
- **D6 —— 守卫减少后，诚实性靠"守卫不冒充覆盖"**：不许留下"看起来在守、其实恒真"的判据
  （本仓已有审计工具专门筛这类，撤守卫时先过一遍）。宁可显式承认某条纪律无守卫。

## Consequences

**收益**

- **判断权回到作者手里**：写作纪律针对的是"读者会不会被误导"，而不是正则是否命中。
- **不再有"纪律守卫自身腐化"这一类维护负担**，也不再出现守卫内部自相矛盾。
- **文档改动的摩擦降到与其它改动一致**，不用为了改一句话去满足发布面标准。
- **从根本上消除数值腐化**：数字不再进文档，就没有"抄了一份会漂的副本"这回事。

**代价（我们放弃了什么）—— 这一节是本文最重要的部分**

- **失去机器兜底，回归靠评审**。最直接的已知风险：`docs/HOW-IT-WORKS.md` 曾写的路由条数
  已经与实际不符（生成物里是对的），撤掉守卫后**这类错误只能靠人发现**。
  本 ADR 接受这个风险，理由是：那条守卫此前**也没能防住它**（该文档不在守卫扫描面内），
  所以真实损失是"少了心理安慰"，而不是"少了保护"。
- **"不写数值"这条没有守卫**。它是纯约定，违反不会变红。缓解手段只有
  文档顶部的一句话免责与评审时的注意力。
- **历史文档不追溯**：归档件与 `CHANGELOG.md` 里的数值**保持原样**。
  它们是账本，描述"当时如何"，改了反而是伪造记录。
- **一次性的清理成本**：现有常青文档里那些已写入的数值要逐条改掉或搬走，
  这不是小工作量（改动面横跨根 README 三份与 `docs/` 顶层多份）。

## 重新考虑的触发线

出现下列情况时，应回来重评（**而不是悄悄把守卫加回去**）：

- 常青文档的数值腐化**重复发生且造成实际误导**，同时评审没能拦住
  ⇒ 届时应考虑的是一条**极窄**的判据（只扫常青层的"数字 + 单位"形态，不解析语义），
  并在本 ADR 里记明为什么窄判据是必要的，而不是恢复措辞词表。
- 文档类守卫撤除后，出现**"跳过与通过同形"**的静默覆盖丢失 ⇒ 那是 D6 被违反，
  应按 D6 修，而不是恢复旧守卫。
- 贡献者规模增长到评审带宽不足 ⇒ 届时应先提高**代码侧**守卫的精度（那里后果可测），
  再考虑文档侧。
