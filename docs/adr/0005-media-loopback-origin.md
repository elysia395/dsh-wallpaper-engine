# ADR-0005: 壁纸媒体由宿主自建的独立 loopback 源提供（Dedicated loopback media origin）

- **Date**: 2026-09-30
- **Status**: Accepted
- **Deciders**: YV3507
- **Amends**: 场景载荷服务族的挂载方式（见 `docs/adr/0001-webwallgl-in-tree-live-renderer.md` 的 D2）

> 实现与围栏不变量在 `lib/index.js` 的 `ensureMediaOrigin` / `handleSceneFiles` 与
> `lib/routes/scene-serve.js` 的文件头；本文只记**为什么需要第二个源**。

## Context

场景与网页壁纸的载荷（`scene.pkg`、`project.json`、网页入口 HTML 及其全部子资源）
最初都从**应用源**出去 —— 也就是宿主插件注册在 DSH webserver 上的同源路由。

这在场景壁纸上是成立的：渲染页是**同源非沙箱 frame**，它的 `fetch` 带着正常的 `Origin`，
DSH Desktop 的能力头栅栏放行。

但**网页壁纸**是另一种处境。它必须运行在严格沙箱里（`sandbox="allow-scripts"`），
而这个沙箱给文档一个**不透明源（opaque origin）**。后果是它的 `fetch()` / XHR
带的是：

```
Origin: null
```

（`img` / `script` / `css` 这类子资源加载不受影响 —— 只有脚本发起的请求带这个头。）

DSH Desktop 的插件路由前面有一道**能力头栅栏**，它会拒绝这类请求 —— 症状是网页壁纸
**直接 403**。也就是说：

- 想让网页壁纸能取到自己的载荷，就必须让它**不经过**插件路由表；
- 但载荷又必须由宿主提供（它只服务已枚举过的壁纸目录，不能放开文件系统）。

这里有一对真实张力：**沙箱隔离**（要安全）与**同源路由的能力栅栏**（要能取到字节）不能同时满足。

## Decision

**宿主自建并监听第二个 loopback HTTP 源**（`ensureMediaOrigin`），壁纸媒体由这个源提供，
从而**绕开插件路由的能力头栅栏**，同时保留宿主侧的目录围栏。

配套决定：

- **D1 —— 两处挂载共用同一段处理逻辑**（`handleSceneFiles(req, res, mount)`）。
  应用源与媒体源的行为必须一致（目录围栏 / CORS / shim 与种子注入 / Range）；
  `mount` **只**影响请求记录，不影响行为。
- **D2 —— 记录策略按挂载分型，因为量级差很多**：应用源逐请求全记（场景 pkg 等，量小）；
  媒体源只记文档型请求与错误 —— 网页壁纸子资源太多，全量记录会把诊断环冲掉。
- **D3 —— 媒体源地址只能以访问器形式跨模块提供**。`mediaOrigin` 是该作用域的**可变量**
  （`ensureMediaOrigin` 会重新赋值），把 `port` / `base` 的值拷进 context 就是一份**陈旧快照**，
  永远报 null。因此对外只给函数（`mediaOriginBase()` / `mediaOriginInfo()`）。
- **D4 —— 起不来时不静默**：绑定失败会记住（不反复重试，否则每次 inventory 都重试绑定），
  诊断留痕 + 一条用户可见提示，并让客户端**回落应用源**（慢但可见），而不是给一张空白。
- **D5 —— 媒体源也要能被观测与手选覆盖**：是否需要它由适配目标收敛（`mediaOriginNeeded`），
  与"宿主形态"的判断共用同一条链，避免出现"网页壁纸该走哪条"的第二处真相。
- **D6 —— 端口是动态的**：监听 `127.0.0.1` 的**随机**空闲端口并对外公布 base。
  固定端口会与用户机器上的其它进程冲突，且冲突表现为"功能偶发失效"。
- **D7 —— 跨源许可是**窄**的**：媒体源只为载荷服务，放行 `Range` 与必要的自定义头，
  `OPTIONS` 直接放行；目录围栏仍然只在壁纸目录内解析目标，越界一律拒绝并留痕。

## Consequences

**收益**

- **网页壁纸能拿到自己的载荷**，同时**没有**放开插件路由的能力头栅栏 ——
  即没有为了功能而削弱其它路由的保护。
- 沙箱隔离得以保留（这正是 ADR-0001 D2 里网页壁纸复用渲染页骨架的前提）。
- 场景壁纸仍走应用源（同源、带能力头），两条路径各取所需，互不牵连。

**代价（我们放弃了什么）**

- **多了一个进程内监听口**：多一份生命周期要管（卸载时关闭、起不来要记住、端口要公布），
  并且它**不在**插件路由表里 —— 因此不会出现在路由索引里，读索引的人容易漏掉它。
- **诊断面变复杂**：请求记录不得不分型（D2），"为什么这张壁纸没加载"需要在两个源之间判断。
- **可变量必须包成访问器**（D3）：这是个容易踩的坑，代码里留了专门的注释警告。
- **适配目标成了前置条件**（D5）：是否需要媒体源与宿主形态耦合，
  于是"桌面壳 vs 原生浏览器"的判断错一处，就会表现成"网页壁纸时好时坏"。
- **端口动态**带来"地址不确定"的调试成本（D6）。

## 重新考虑的触发线

- **上游不再对插件路由做能力头栅栏，或为不透明源提供豁免** ⇒ 第二个源的存在理由消失，
  应立刻回来删除它（这是最值得推翻本 ADR 的触发线）。
- 网页壁纸改为**不需要严格沙箱**（例如上游提供受控的同源执行环境）⇒ 同样可回到单源。
- 媒体源与载荷服务族的耦合继续增长（更多路由需要"两个源"）⇒ 说明该把"源"抽象成
  一等概念，而不是继续在路由里分 `mount`。
