# ADR-0012: 插件拆分走「一 bundle 多组件行」，并以降低复杂度为目标（plugin split: one bundle with per-component rows, judged by complexity reduction）

- **Date**: 2026-10-13
- **Status**: Amended by [ADR-0013](./0013-component-toggle-soft-goal-chunks.md)、[ADR-0014](./0014-goal-reanchor-and-contract-tightening.md)（0014 把 D1 的核心目标由"降复杂度"一件扩为**三件并列**：降复杂度 / 锚定模块边界 / 解耦合）
- **Deciders**: 用户（产品口径）+ 实现（本仓）
- **Related**: [ADR-0002](../adr/)（设置的单一真源）、
  [ADR-0003](../adr/)（浏览器半边靠构建期内联）、
  [ADR-0004](../adr/)（守卫分两档）
- **实施计划**: [`docs/wip/BUNDLE-SPLIT.md`](../)（尚在进行的工作住 `docs/wip/`）

## Context

### 用户口径（本决策的动机）

- 起因：「当前插件正在逐渐臃肿，我希望发起一轮大重构，将插件拆分为多个插件组成的插件包」，
  并要求参照 `dsh-ops` 的设计判定哪些功能适合独立。
- 目标澄清：对「浏览器侧组件能单独关是不是需求」，用户答：
  **「「浏览器侧组件能单独关」本身不是一个需求，更像一个结果，拆包的核心目标是降复杂度」**。
  ⇒ 这条把「可独立开关」从验收条件降级为**可能的结果**，直接决定了本 ADR 的 D4。

### 可测事实（符号名 / 文件路径作锚点，不写行号与数值）

1. **宿主支持「一个包 = 一个 bundle = 多行」**：`package.json` 声明 `dsh.bundle.patch`，patch 是**顶层 YAML 数组**，
   其中 `- insert:`（**不带 `id`**）把若干行追加到根 `include` 上；每行是一个 loader entry
   （`{ id, name, config, group, disabled }`）。行**未激活也能显示**标题 / 描述 / 图标 ——
   元数据走**导出资源**（`readPluginMeta()` / `metaOf()` 读 `<specifier>/locale/<lang>.json` 与
   `<specifier>/package.json`、`iconOf()` 读顶层 `icon`），**不 import 插件代码**。
   用户可在插件管理器里**单独开关某一行**（`setPluginEnabled()` → `writePluginEnabled()` 保留注释地改
   profile 的 `cordis.patch.yml`）。出处：宿主随包 `host-plugin.md`、`dsh-app-boot`、`dsh-host-plugin-inventory`、
   `dsh-plugin-manager`。
2. **客户端半边是「包级」的**：`dsh-client-modules` 用 `exactPackageSpecifier()` 只认**裸包名或恰好两段的
   scope 名**，再用 `nearestPackage()` 向上找第一个 `name === 包说明符` 的 `package.json`，最后
   `table.set(packageName, …)` ⇒ **一个包只产生一个客户端 graph row（id = 包名）、一个开关、一个 UI 贡献面**。
   子路径行（`pkg/sub`）**完全不参与** `dsh.client` 扫描，也拿不到自己的 `dsh.client`。
3. **本仓现状：复杂度集中在两个文件 + 一处共享资产**。
   - 宿主门面 `lib/index.js` 里混着大量**与装配无关**的实现（Steam / WE 发现、转码与 ffmpeg、
     数据目录与 config 内核、HTTP body 内核），而 `lib/routes/*.js` **每个文件的入边恰好是 1**（只有门面 import 它）
     ⇒ 路由族事实上已经是插件。
   - 浏览器半边 `src/client.js` 是最大的客户端文件；而浏览器半边**没有模块系统**（靠构建期内联，
     见 [ADR-0003](../adr/)），拆分手段天然受限。
   - 设置是**单一扁平命名空间**且 `PUT /settings` 是**整段规范化副本覆盖**（`lib/routes/settings.js`）
     ⇒ 两个组件各写一次 `settings` 段必然互相丢键；`lib/settings-schema.js` 又是宿主与客户端**共用的唯一内核**
     （[ADR-0002](../adr/)）。
4. **`dsh-plugin.json` 与 `patchReload` 在运行时都没有消费者**（全量检索 `.js` 零命中）；
   profile 的 `cordis.yml` **不是事实来源**（每次启动被重写），只许改 profile 的 `cordis.patch.yml`。

## Decision

- **D1 核心目标是降低复杂度**，「组件能单独开关」是手段或副产品，不是验收条件。
  凡**不改善**既定复杂度度量（最大文件体量、门面内非装配代码占比、跨组件共享同一读改写路径的设置键数、
  守卫硬编码清单条数、「一个功能族 → 哪些文件」的唯一性）的拆分，**一律不做** —— 哪怕它能变成一行可开关的组件。
  度量与复算命令见 [`docs/wip/BUNDLE-SPLIT.md`](../) §3（**不写进本 ADR**，见 ADR 的"不写数值"纪律）。
- **D2 终态取「单包多行」**（一个包 + N 个组件行 + **一个**客户端半边）：行必须**不带 `id`** 地顶层 `insert`
  （否则不可寻址、不可单独开关）；**必须保留一个 `name` 恰为裸包名的行**承载浏览器半边，否则客户端半边静默消失。
- **D3 组件化之前先做库化与内核化**：先**纯搬移**（零行为变化、产物零字节变化），把门面里与装配无关的段落
  与新组件的落点定下来；`settings` 先分区（per-component 子段 + 一次性**幂等**迁移，`/settings` 改成按段合并）。
  **设置可切分是真组件的先决条件** —— 跳过它直接拆，等于把「两个组件互相丢键」写进架构。
- **D4 不做「多包 monorepo」**。它唯一买到的是**浏览器侧的独立开关**，而该能力已被判定不是需求（见 Context 的
  用户口径）；代价却是：发布面按包数翻倍、踩在宿主明确声明可能无预警变更的 `dsh.client.*` 上、
  构建脚本要按包循环出多份产物、守卫与生成物大面积重写。将来若因**首屏体量**或**独立发布**重启，
  按 [ADR-0003](../adr/) 的触发线**另写一份 ADR**，不改写本 ADR。
- **D5 不推翻 [ADR-0003](../adr/)**：浏览器半边继续**单包构建期内联**；
  客户端懒加载 / 分块（"方案 B"）不在本轮范围。
- **D6 组件元数据按宿主契约写**：`exports` 三连（`./<c>`、`./<c>/package.json`、`./<c>/locale/*.json`）；
  `locale/` 目录**只放语言名文件**（否则整行元数据丢、显示裸 specifier）；**每个组件各带一份同目录图标**；
  **不写 `dsh-plugin.json`**（运行时零消费者），将来若要上架市场再补。
- **D7 兼容与安全**：保留旧行 id（老用户 profile 的 patch 里已有它）；`files` 是**逐文件**白名单 ⇒ 新增文件逐条登记；
  覆盖既有行时必须给**完整** `config`（覆盖是整体替换、不深合并，否则迁移标记会丢、迁移会重跑）；
  每行独立迁移标记，新增组件必须同步其名单；**先校验后迁移**。

## Consequences

**收益**

- 复杂度按可复算的指标下降：门面从"3,000 行上下的巨石"变成"装配 + 协议聚合"，且每个功能族有唯一落点。
- 宿主侧获得**每个组件的显示元数据与独立开关**（插件管理器里是 N 行，而不是一行黑白开关）。
- 「加一个功能」有唯一答案（新组件目录 / 新注册表项），不必先读完整门面。
- 路由族已有的形状（入边 = 1）与「扩展」页签已有的模块注册表被显式承认，改造顺着现有接缝走。

**代价 / 我们放弃了什么**

- **放弃了"浏览器侧组件各自开关"**。一个包只有一个客户端半边 ⇒ 关掉一行只关宿主半边，UI 侧只能靠
  设置项或路由探测降级。这是 D4 的直接后果，是**有意的**：那个能力不是需求。
- **本轮不解 `src/client.js` 的体量问题**（无模块系统 + 构建期内联的既有边界），只搬扩展三项的处理器。
- 包体积随组件数增长（每个组件各带一份图标，且图标不能共享 —— 宿主要求 realpath 后仍在该清单同目录内）。
- 守卫改造面大：产物 `lib/client.js` 与三份生成物（路由索引 / 守卫映射 / 令牌契约）是大量守卫的输入，
  被读文件一搬家就可能让守卫整条崩或静默失去覆盖 ⇒ 每一步都要重新证明"牙还在"。
- 上游同时演进时的冲突面（缓解：先纯搬移、面窄、每步独立提交可单独 revert）。

## 重新考虑的触发线

1. **首屏 / 包体量成为用户侧首要抱怨，且代码分割成为必需** —— 这正是
   [ADR-0003](../adr/) 写下的触发线之一；此时重新评估"方案 B"（同包内分块）
   与多包（方案 C）。
2. **宿主开始支持子路径行各自的客户端半边**（组件级 `dsh.client`） —— 则 D4 的前提（多包是唯一出路）消失，
   需要重写一份 ADR 说明新形态。
3. **某个组件需要独立发布节奏或独立版本号** —— 单包多行做不到，须重议多包与发布面。
4. **设置分区被证明不可行或代价过高** —— D3 的前提动摇，组件化的落地方式必须重议（而不是绕过它）。
5. **`docs/wip/BUNDLE-SPLIT.md` 的计划收口时**，若实际收益与度量目标差得远，回来修订本 ADR 的 D1 / D2。
