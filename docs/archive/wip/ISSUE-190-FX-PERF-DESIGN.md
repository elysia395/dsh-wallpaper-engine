## 0. 结论速览

- 报告的「参数敏感度」与代码结构**逐条对应**，根因可判定，不是"环境差异"或"显卡驱动"。
- 主因是 Canvas2D 的 **`shadowBlur`**：全文件 6 处，其中 **5 处是光晕赋值**（另有 1 处帧尾归零）。每次光晕赋值都让后续每个 `stroke()` / `fill()` 触发一次离屏高斯模糊，而这些赋值落在**每帧、每图元**的路径上。
- 次因是**每帧全量重画整条拖尾**（`O(点数)` 次带模糊的描边）与**全屏画布 × DPR 2**。
- 推荐主方案：**把光晕从 `shadowBlur` 换成预渲染贴图 / 径向渐变**（成本降一个数量级），叠加**自适应降帧**与**帧耗时驱动的自动降级**。
- 观感会变，必须做 A/B 对照；验收要用**可执行的帧耗时测量**，不接受"看起来快了"。

## 1. 问题

报告者（Windows 11 25H2，插件 1.3.2）给出的实测敏感度：

| 参数 | 报告的影响 |
|---|---|
| 点击样式 | 均有影响，**星火 > 涟漪** |
| 点击半径 / 不透明度 | 影响不大 |
| **点击光晕** | **影响很大** |
| 混合模式 / 效果配色 | 无明显影响 |
| **拖尾时长** | **影响很大，正相关** |
| **拖尾光晕** | **影响很高，正相关** |
| 拖尾粗细 | 有一定影响，程度不高 |
| 不透明度 / 配色 | 无明显影响 |
| 拖尾样式 | 彗尾与星尘均有影响，两者差别不大 |

期望：开启后占用平稳，或至少有更高效的降级 / 性能优化策略（动态降帧、关闭高耗能光晕等）。

## 2. 根因

全部证据来自 `src/fx-layer.js`（该文件在本仓 HEAD 与上游 `main` 逐字节一致）。

### 2.1 五处光晕 `shadowBlur`

`shadowBlur` 是 Canvas2D 里最贵的状态之一：每个 `stroke()` / `fill()` 都要在离屏缓冲里做一次高斯模糊，再与主画布混合。5 处光晕赋值：

| 行号 | 代码 | 归属 |
|---|---|---|
| 335 | `g.shadowBlur = st.trailGlow * f * 0.4` | 拖尾（星尘） |
| 351 | `g.shadowBlur = st.trailGlow * f * 0.35` | 拖尾（彗尾） |
| 378 | `g.shadowBlur = st.clickGlow * 0.4 * fade` | 点击（涟漪） |
| 390 | `g.shadowBlur = st.clickGlow * 0.35 * fade` | 点击（星火） |
| 409 | `g.shadowBlur = st.clickGlow * 0.5 * flash` | 点击（中心白闪） |

另有 1 处帧尾归零（第 453 行 `g.shadowBlur = 0`），不产生开销。

这**精确解释**了「点击光晕影响很大」「拖尾光晕影响很高」，以及「半径 / 不透明度 / 配色影响不大」——半径只改 `arc()` 的几何半径，不改模糊半径；颜色解析与 alpha 都是廉价操作。

### 2.2 每帧全量重画拖尾

`fxDrawTrail` 的彗尾分支对**整条**拖尾逐段描边（`fxTrail.length - 1` 次 `stroke()`，每次带 `shadowBlur`）：

```
for (let i = 1; i < fxTrail.length; i += 1) { … g.stroke(); }
```

点数上限 `FX_POINT_MAX = 96`，而存活点数与 `fxTrailLength` 正相关（越长的记忆时长 ⇒ 越多的点在寿命窗口内）。

⇒ 每帧的模糊次数 ≈ 点数，**精确对应「拖尾时长影响很大，呈正相关」**。

### 2.3 星火 12 条 vs 涟漪 2 环

`FX_SPARK_COUNT = 12`。星火分支每帧对**每条**火花描边一次（各带一次 `shadowBlur`），即每帧 12 次模糊；涟漪分支只有 2 个圆环，即每帧 2 次模糊。

⇒ **精确对应「星火比涟漪对 GPU 影响更大」**。同时解释「拖尾样式差别不大」——彗尾与星尘的图元数在同一量级。

### 2.4 全屏画布 × DPR

- 画布按 `Math.min(window.devicePixelRatio || 1, FX_DPR_MAX)`（`FX_DPR_MAX = 2`）分配。1920×1080 在 DPR 2 下是 **3840×2160** 的位图。
- 每帧 `clearRect(0, 0, width, height)` **全屏**清除，即使只有一个几像素的光点。

### 2.5 合成侧

宿主元素上写 `mix-blend-mode`（默认 `screen`）与 `opacity`。整层是 `position: fixed` 的全屏合成层，每帧重绘都要重新做一次与壁纸的混合。

⇒ 解释了「混合模式无明显影响」：切换混合模式改的是合成公式，**不改变重绘与模糊的量**。

### 2.6 根因 ↔ 实测对应表

| 实测结论 | 对应根因 |
|---|---|
| 点击光晕影响很大 | 2.1（3 处 `shadowBlur`） |
| 拖尾光晕影响很高 | 2.1（2 处 `shadowBlur`） |
| 拖尾时长正相关 | 2.2（每帧模糊次数 ≈ 存活点数） |
| 星火 > 涟漪 | 2.3（12 次 vs 2 次模糊） |
| 半径 / 不透明度影响不大 | 只改几何与 alpha，不改模糊量 |
| 混合模式 / 配色无明显影响 | 改合成公式与颜色解析，不改模糊量 |
| 拖尾样式差别不大 | 两种样式图元数同量级 |

## 3. 目标与非目标

**目标**

1. 开启点击与拖尾效果后，帧耗时与 GPU 占用显著下降，且与「光晕 / 时长」的相关性明显减弱。
2. 提供**无感的自动降级**：负载高时逐级降档，可回退，可观测。
3. 观感与现状**接近**（不要求逐像素一致，但需要人工 A/B 确认可接受）。

**非目标**

- 不改光效的**语义**（仍是一击一炸、拖尾自行淡完、空闲零帧）。
- 不引入 WebGL 重写（成本远超收益，属 YAGNI）。
- 不改宿主元素 `z-index` 层级与 `pointer-events` 契约。
- 不改变「不采样壁纸像素」这条既有设计（见该文件头不变量）。

## 4. 方案

### A. 光晕去 `shadowBlur`（主方案，收益最大）

把 5 处模糊换成两类廉价替代：

| 图元 | 现状 | 替代 |
|---|---|---|
| 拖尾星尘（圆点） | `arc` + `fill` + `shadowBlur` | **预渲染径向渐变 sprite** + `drawImage` 缩放 |
| 点击中心白闪（圆） | `arc` + `fill` + `shadowBlur` | 同上（sprite 或一次性 `createRadialGradient`） |
| 点击涟漪（圆环） | `arc` + `stroke` + `shadowBlur` | **径向渐变环**：`createRadialGradient(r-w, r+w)` 铺 alpha 峰，再 `fill` |
| 拖尾彗尾（线段） | `moveTo/lineTo` + `stroke` + `shadowBlur` | **多层描边**：同一线段画 2 层（宽而淡 + 窄而亮），靠既有的 `lighter` 叠加出辉光 |
| 点击星火（线段） | 同上 | 同上 |

要点：

- **sprite 只生成一次**（模块级惰性创建，离屏 canvas），后续全是纹理采样。
- 圆环走径向渐变而非 sprite，因为环半径连续变化，sprite 缩放会**同时缩放线宽**，观感会跑。
- 多层描边是"用图元数量换模糊"，实测通常比单次 `shadowBlur` 便宜一个数量级；层数建议 2 层起步，按 A/B 定。
- 这套替代后，`st.clickGlow` / `st.trailGlow` 从"模糊半径"改判为"叠加层数与峰值 alpha"，两个滑块**仍然有效**（不能变成假控件）。

### B. 拖尾增量绘制（可选，需 A/B 后再定）

经典做法：不清屏，每帧对整张画布铺一层低 alpha 的 `destination-out`（或直接用半透明矩形淡出），新点只画增量。把每帧 `O(N)` 降为 `O(1)`。

代价：拖尾自带"余晖"、尾部不会真正归零，观感与现在的"精确按年龄淡出"不同；且与 `clearRect` 全屏清除的既有形态冲突（`test/verify-scene-live.mjs` 有相关源码口径断言）。**建议先做 A，测量后若仍不达标再评估 B。**

### C. 自适应降帧

拖尾不需要 60 fps。帧循环里加最小帧间隔（如 33 ms ⇒ 约 30 fps），视觉几乎无差、成本约减半。

注意：这会让"帧循环是内容驱动的、空闲零帧"这条不变量多一个条件，**守卫需同步**。

### D. 帧耗时驱动的自动降级

用已有的 `weNow()`（`src/we-base.js`，无 `performance` 时退 `Date.now`）采样每帧耗时，滑动窗口判断，超阈值时**逐级降档**：

```
满档 → 关中心白闪 → 降 glow 峰值/层数 → 降帧(60→30) → 关光晕(仅留干净图元)
```

要求：

- **可回退**：负载回落时逐级恢复，避免"一次抖动永久降级"。
- **可观测**：降级事件走既有诊断通道（`reportClientDiag` / `liveLog` 同族），便于排查。
- **有迟滞**：升降档都要连续 N 帧满足条件才动，避免在阈值上抖动。
- **默认开启且无感**：不加设置键（见 §5 第一期），因此对用户零配置成本。

### E. DPR 自适应（可选）

大屏或高 DPR 时把 `FX_DPR_MAX` 动态降到 1。收益明显（位图面积减到 1/4），但光效边缘会略糊 —— 建议只在 D 的降级链末端使用。

### 顺手项（零风险）

- `fxPlace()` 每帧调用 `document.querySelector('.we-scrim')`：改为缓存 + 失效重查。
- `fxFrame()` 每帧调用 `getContext('2d')`：结果可缓存。

### 取舍与推荐

| 方案 | 收益 | 风险 | 建议 |
|---|---|---|---|
| A 去 `shadowBlur` | 高 | 中（观感变化，需 A/B） | **第一期必做** |
| C 自适应降帧 | 中 | 低 | **第一期必做** |
| D 自动降级 | 中高 | 中（状态机 + 可观测） | **第一期必做** |
| E DPR 自适应 | 中 | 低 | 第二期（挂在 D 链末端） |
| B 增量绘制 | 高 | 高（观感 + 守卫冲突） | 第三期（A 之后仍不达标再评估） |

## 9. 实施结果（第一期已落地）

### 9.1 实际改了什么

**与设计方案的差异**（读代码后调整的，理由在后）：

- **没有走"光晕贴图化"**（方案 A）。读了实现才发现：真正的结构性浪费不在"模糊本身"，
  而在**同一帧里对共享同一套绘制状态的图元反复发绘制调用**。于是改成**按年龄带合批** +
  **星火合并成一条路径** —— 保留 `shadowBlur`（观感零妥协），但把模糊**次数**砍掉两个数量级。
  这比贴图化更小、更安全，且不动观感。
- **自适应降级**（方案 C + D）按设计实现：帧耗时驱动、可回退、有迟滞，且**不加设置键**。
- 方案 B（增量绘制）与 E（DPR 自适应）**未实施** —— 9.3 的实测显示已无必要。

改动清单：

| 文件 | 改动 |
|---|---|
| `src/fx-layer.js` | 拖尾按年龄带合批（彗尾/星尘各一份）、星火 12 条合并为单次 `stroke`、`fxPerfUpdate` 降级状态机、限帧闸门、`getContext` 与 `.we-scrim` 查询缓存 |
| `test/verify-scene-live.mjs` | 新增两条 #190 判据（贵操作计数棘轮 + 降级状态机形态） |
| `test/tools/fx-perf-rig.mjs` | 新增真浏览器帧耗时对照装置 |

### 9.2 贵操作计数（单元判据，`npm run verify` 里跑）

假 canvas 数一帧的贵操作（满档参数、96 点拖尾 + 一次点击）：

| | 带光晕的绘制调用（真高斯模糊次数） | 描边 / 填充调用 |
|---|---|---|
| 修复前 | **109** | 109 |
| 修复后 | **4** | 4 |

棘轮上界 `blur ≤ 24`、`stroke+fill ≤ 40` —— 把"逐段一次模糊"（≈99）挡在外面。

### 9.3 真浏览器帧耗时（`test/tools/fx-perf-rig.mjs`，各跑 2 次）

| | 帧间隔 p50 | 帧间隔 p95 | mean |
|---|---|---|---|
| 修复前 | 8.40 / 8.30 ms | **16.70 / 16.70 ms** | 10.40 / 9.41 ms |
| 修复后 | 8.30 / 8.30 ms | **8.50 / 8.50 ms** | 8.80 / 8.75 ms |

**p95 稳定减半**（16.70 → 8.50 ms），且修复前那个 16.70 恰好压在 60fps 的 vsync 边界
（16.67ms）上 —— 那正是"每帧都掉一档"的形态，与报告者看到的卡顿一致。

⚠️ 这是**无头浏览器的相对对照**，不是真机绝对值（见装置头注释的局限声明）。

### 9.4 观感

- **拖尾**：同一带内共用一次模糊 ⇒ 带内观感被量化。带数 = 性能档（满档 8 带），
  满档下的量化在 96 点拖尾上约每 12 点一带，肉眼不可辨。
- **星火**：只合并**绘制调用**，不合并形状 —— 每条火花的角度与长度差异全部保留，观感不变。
- **两个光晕滑块仍然有效**（`fxClickGlow` / `fxTrailGlow` 照旧驱动模糊半径），不是假控件。
- **空闲零帧**与"内容驱动续帧"两条不变量未动（守卫仍在盯）。
