## 1. Context —— 处境与约束

### 1.1 起因

「雾化」滑杆的覆盖面与它的名字不符：它只对**对话栏框架**、**左侧栏覆盖**、**设置窗口**
与插件的两个浮层有效；正文里的内容面（markdown 代码块家族、思考触发条）根本没有模糊层；
侧栏则有一条自己的模糊滑杆。用户视角下这是「同一个概念在不同位置上语义不一致」。

顺着这条线清点，发现不是一处标签问题，而是**三处同名不同实**。

### 1.2 三处同名不同实（可复算）

判据住在代码里，读这三处即可复现：

| # | 概念 | 对话栏那套 | 侧栏那套 | 冲突形态 |
|---|---|---|---|---|
| C1 | **透明度曲线** | `glassAlpha` → `--we-glass-alpha`，曲线在 `applyEffects` 内 | `sidebarAlpha` → `--we-sidebar-alpha`，另一条曲线 | 两个同名概念、两条不同曲线、区间差一个数量级 |
| C2 | **玻璃色** | `glassColor` → `--we-surface-tint-*` | `sidebarColor` → `--we-sidebar-color` | 两套独立配色，互不跟随 |
| C3 | **颜色浓淡** | 无独立项 | `sidebarTint` **由 `sidebarAlpha` 派生**（`src/effects.js`） | 一个滑杆带两个效果：调透明度会连带改染色浓度 |

再叠加**饱和度**：`--we-saturate` 是常数，而 `--we-sidebar-saturate` 由 `sidebarBlur` 派生
（`src/effects.js`）——同一个「饱和度」在两侧成因不同。

**侧栏今天实质上已是一套"半独立配置"**，靠几组专用键加三条派生曲线拼出来，
而仓库里**没有任何一处**描述「侧栏与全局是什么关系」。这正是要重构的东西。

### 1.3 必须保住的既有设计

- **可读性下限**（`--we-readability-*` + `weClampSurfaceColor`）是 `README` 对用户的公开承诺，
  由 `test/verify-readability.mjs` 的对比度网格复算，**只有一个实现**。
- **「玻璃保真度」是作者明确要求保留的配置**（用户口径），它不是一个内部系数：
  观感上它决定**黑白玻璃 ↔ 透明/带色玻璃**——满档时玻璃色被钳到接近原生背景（保可读性），
  接近 0 时原色直出（一方面美观，另一方面让「玻璃颜色」这个滑杆真正有意义）。
  因此它**必须是用户可见、可调的旋钮**，且理应**可被各面独立覆盖**（见 D1）。
- **两段式构造（D1 的前提）**：`weClampSurfaceColor(hex, theme, fidelity)` 的第一段
  （跑满档地板、二分求最暗/最亮可用色）**与 `fidelity` 无关**——它只回答"这个颜色在完整地板下
  能不能直出"，用的是满档常量；`fidelity` 只出现在第二段，即"把钳制结果向用户原色线性回退"的
  **系数**。同一函数头注释写明了这一点。**这条性质决定了保真度可以按面独立而不复制数学**（见 D1）。
- **澄清一个易误解点**：`--we-glass-fidelity` 是 `body` 级的，所以设置窗口**关掉玻璃开关时它
  形式上仍生效**，只是那时窗口没有玻璃配方、看不出差别。

### 1.4 约束

1. **默认逐位不变**：老用户升级后观感必须零变化，且要能被机器验证（不能只靠承诺）。
2. **判据只针对代码**（[`adr/0007`](../adr/0007-machine-checks-target-code-not-prose.md)）。
3. **不写会漂的数值**（[`adr/README.md`](../adr/README.md) §不写数值）：本文给复算方式，不给数字。

## 2. 面的分类（三类，不是一类）

清点时最重要的结论：**"要不要玻璃"这件事在三个位置语义完全不同**，不能塞进同一个开关系列。

| 类 | 面 | 开关语义 | 关闭后看到什么 |
|---|---|---|---|
| **甲 · 启用玻璃** | 对话栏框架 · dsh-better-sidebar 侧栏 · 设置窗口 · 插件浮层 | 「加玻璃」**对**「恢复宿主纯色」 | 宿主原始**不透明底色**（纯色块） |
| **乙 · 背景还原** | **左侧栏覆盖**（`leftSidebarGlass`） | 「还原背景」**对**「宿主纯色填充」 | **壁纸原样透出**（不是纯色块） |
| **丙 · 内容面** | markdown 代码块家族 · 思考触发条 | 无独立显示开关（随壁纸） | — |

**乙为什么必须独立成类**（用户口径）：其它面的「启用玻璃」关闭等于**恢复纯色**；
左侧栏那一处关闭等于**恢复背景**——它不会变成纯色块，而是单纯显示壁纸背景。
两者是**方向相反**的语义，所以左侧栏覆盖**不进「启用玻璃」系列 UI**，自成一类。
（技术上也印证：它今天读的是全局 `--we-surface-tint-*`，与甲类共用参数，但它的"关"状态
是别的面所没有的透明态。）

## 3. 目标架构

```
┌─ 全局玻璃配置（一份）───────────────────────────────┐
│  釉层四件套：玻璃颜色 · 透明度 · 模糊 · 饱和度          │
│  保真度：可独立，但默认继承全局                        │
└────────────────────────────────────────────────────┘
        │  默认：每个面都继承全局
        │
        └─ 每个面：启用玻璃（显示开关）── 是「独立控制」UI 的**前提**
                     └─ 独立控制（参数覆盖）── 开 ⇒ 读本面私有值
```

### 3.1 两个概念分开，但**前者是后者的显示前提**（用户口径）

| 概念 | 回答 | 与另一个的关系 |
|---|---|---|
| **启用玻璃** | 这个面**要不要**玻璃？ | **关 ⇒ 该面的「独立控制」UI 不显示**；开 ⇒ 才谈得上用谁的参数 |
| **独立控制** | 这个面**用谁的参数**？ | 只在「启用玻璃」为开时才可配置 |

这条依赖方向本身是合理的：一个面连玻璃都没有，"它用哪套玻璃参数"就是无意义的配置项。

### 3.2 D1 **保真度允许独立**，且不复制可读性数学

原先的顾虑是"每个面各持一份保真度 ⇒ 把同一套 WCAG 数学复制 N 份 ⇒ 漂移源"。
**该顾虑不成立**，因为 §1.3 那条性质：

- **第一段（贵的那段）**：满档地板的钳制 + 二分搜索 + 对比度判定 —— 只依赖
  `(玻璃色, 主题)`，**与保真度无关** ⇒ 全局算**一次**即可（`clamp1(hex, theme)`）。
- **第二段（廉价的插值）**：`result = clamp1 · f + 原色 · (1 − f)` —— 逐通道线性混合，
  以保真度为**系数** ⇒ 每个面各传自己的 `f` 即可，**没有第二份数学**。
- **下限覆盖度**：`--we-readability-floor` = 下限常量 × 保真度，是纯 CSS 乘法 ⇒ 每面一个变量即可。

⇒ 每面需要的是**两个变量**（本面的 `--we-*-surface-tint*` 与本面的 `--we-*-readability-floor`），
而**钳制实现仍然只有一份**。

**但必须钉一条一致性不变量**：某个面用它自己的保真度 `f_s` 时，
**它的釉色混合系数与它的下限覆盖度必须用同一个 `f_s`**。
否则会出现"釉色按低保真回退、地板却按满档压着"这种自相矛盾的合成（观感上就是
"颜色对了但底下还是白的/黑的"）。**这条已有判据**：`verify-glass-surfaces` 第 ⑤ 组
（实现与扰动自证的记录见 §4.9）。

> ⚠️ **P3 实测修正（重要）**：上面这段的"每面两个变量"听起来可以由
> "在共享规则里插一层变量名"实现 —— **那条路不成立**，已在 P3 试过并撤回。
> 原因：可读性契约被两条既有判据钉在**固定文本形状**上
> （`verify-readability` F2a 的 `^` 锚定 + `verify-softrender` E2 的逐字共享），
> 而"改 CSS 写法"必然动到那个形状。详见 §4.6。
> ⇒ **按面独立只能靠"改全局变量的取值来源"**（侧栏那条路），
> 这也意味着**与全局共用同一批 CSS 变量的面（设置窗口 / 左栏 / 浮层）要么改不动，
> 要么得先把它们自己的变量从共享规则里拆出来**（那是另一件更大的事）。

### 3.3 D2 复用已有的每面独立值，不新建平行键

侧栏那几组既有键（`sidebar*` / `sidebarContent*`）**不改名、不改语义**，只是被"认领"为该面的
独立值。迁移不需要值转换，也就没有"迁移把用户观感改掉"的风险。

### 3.4 简化配置 vs 复杂配置（用户口径）

「设置窗口」与「侧边栏设置」今天各自是**复杂配置**，而新的"全局 + 每面覆盖"是**简化配置**。
两者是同一个能力的两种表达，必须明确谁覆盖谁、哪些参数**只**落复杂配置。

实测每个面实际消费的釉层参数（复算方式见 §9）：

| 面 | 颜色 | 透明度 | 模糊 | 饱和度 |
|---|---|---|---|---|
| 对话栏框架 | ✅ | ✅ | ✅ | ✅ |
| 左侧栏覆盖（乙类） | ✅ | ✅ | ✅ | ✅ |
| 侧栏（含右栏面板） | ✅（自己的） | ✅（自己的） | ✅ | ✅（由模糊派生） |
| 设置窗口 | ✅ | ✅ | ✅ | ✅ |
| 插件浮层 | ✅ | ✅ | ✅ | ✅ |

**四件套在每个面上都有消费点**，所以简化配置的公共参数集就是完整四件套 —— 不存在
"某个面上某一项无意义"的情况。于是权衡点变成：

- **简化配置**：四件套 + 保真度，**每面一行**（同一形态，学习成本一次）。
- **复杂配置**：可以继续持有该面特有的东西 —— 例如侧栏的**内容面**（编辑器 / 终端）
  另有自己的透明度与底色；这类"面内部的第二层"不必强行塞进简化配置的一行里。

## 4. Schema 设计

### 4.1 结构：一张**两层**的「启用集合」（P1 已落）

```js
// 已实现（P1）——默认空对象 ⇒ 每个参数都继承全局，行为逐位不变
glassOverrides: {
  // 形状：{ <面>: { <参数>: true, … }, … }
  // 缺省 = 该参数继承全局釉层值；置 true = 该参数改读它**自己**的既有键。
  // 例（P2 迁移后的侧栏）：
  //   { sidebar: { blur: true, color: true, transparency: true } }   // fidelity 未列 ⇒ 跟全局
  //   { chatFrame: { fidelity: true } }                              // 其余参数跟全局
}
```

**为什么是两层而不是一层布尔映射**（这是 P1 实施中对原方案的一处修正）：
实测的既有独立性是**按参数**的，不是按面的 —— dsh-better-sidebar 有自己的模糊 / 颜色，
**保真度却跟全局**；对话栏框架正好相反（只有保真度是自己的）。一层映射表达不了
"某个面的某个参数"，而那正是现状。因此：

> **`global` 不再是一个"档位"，而是"每参数缺省继承"** —— 「继承与否」成为唯一的轴，
> 原方案里的"档位"概念退场。

**没有平行参数树**（原方案的 `override: { sidebar: { color, alpha, blur } }` **不需要**）：
参数值本来就是既有键（`sidebarColor` / `sidebarBlur` / `chatGlassFidelity`…），
本键只回答"读谁" ⇒ **不存在两份真源**。这就是 D2 的本意。

消毒口径（`lib/settings-schema.js` 的 `readBoolMapTree`）：只收 `true`、**空子树剪掉**、
深度上限 3、键名限长 ⇒ 键集恒等于"启用集合"。

### 4.2 四条纪律

1. **旧键一个都不删、不改语义**（配合 D2）。
2. **新增项缺省 = 今天的行为**；因此 golden 夹具的漂移**只应来自新增键**，其余必须是零漂移
   （`test/fixtures/settings-sanitize-golden.json` + `test/verify-client.mjs`）。
3. 某面需要新参数时，**优先让它复用已有键**；只有确实没有既有键时，才新开一个顶层键
   （不要建"全局 / 私有"两份同义键 —— §4.1 的"读谁"模型就是为了避免这件事）。
4. **保真度按面独立时，釉色系数与下限覆盖度必须同源**（§3.2 的不变量）——
   实现上就是"该面的 floor 变量由该面的保真度算出"，不允许一处读私有、另一处读全局。

### 4.3 P1 的实施记录（结构已落、行为未变）

- `KINDS.glassOverrides = { kind: 'boolMapTree' }` + `DEFAULTS.glassOverrides = {}`；
  `readOne` 加分发、`readBoolMapTree` 实现递归消毒。
- golden 夹具按既有 `note` 约定补入新增键（33 个期望对象，**纯插入**、其余键零漂移）。
- `npm run verify` / `verify:docs` / `smoke` 三档全绿 —— 这是"默认逐位不变"的机器证据。

### 4.4 P2 的实施记录（既有独立性显式化 + 取值解析器）

**做了什么**：`src/effects.js` 增加一个取值解析器 ——

```js
glassOverrideOn(面, 参数)   // 查 selection.glassOverrides
glassValue(面, 参数, 自己键的值, 全局键的值)   // 启用独立读自己，否则读全局
```

侧栏那 5 个参数（`blur` / `color` / `transparency` / `saturate` / `sheen`）与侧栏内容面
那 2 个（`color` / `transparency`）全部改经它取值；`DEFAULTS.glassOverrides` 把
**既有事实**显式记进来：

```js
sidebar:        { blur: true, color: true, transparency: true },   // fidelity 未列 ⇒ 跟全局
sidebarContent: { color: true, transparency: true },
```

**为什么解析发生在 JS 而不是靠 CSS 变量缺省值**：侧栏那条 CSS 用
`color-mix(… var(--we-sidebar-color) … var(--we-sidebar-tint) …)`，变量一旦缺失**整条声明
会被丢弃**（侧栏变全透明）。所以"回退"必须写成"写另一个值"，不能是"不写"。
（各 `--we-sidebar-*` 在 CSS 里都有兜底，所以 `clearEffects` 里撤销它们本身是安全的。）

**等价性证据**（`.test-cache/p2-equivalence.mjs`，只读取证）：把重构前后的 `applyEffects`
在同一替身上各跑一遍、比对它写过的每一个变量 ——

- 33 个 CSS 变量**逐字节相同**、body 属性相同、`removeProperty` 序列相同；
- **反向探针**：把侧栏三项的独立控制关掉 ⇒ `--we-sidebar-blur` 真的变成全局 `blur`、
  `--we-sidebar-color` 变成全局 `glassColor`、`--we-sidebar-alpha` 从 0.137 变成 0.248
  （由全局 `glassAlpha` 算出）⇒ 解析器确实在读开关，不是碰巧走了同一支。

**顺带记事**：这轮证明 `--we-sidebar-alpha` 是死变量（P0 的登记表已记），
但它仍被设置与撤销 —— 归 P4 一并清理，避免在行为等价性这一轮里混入无关改动。

### 4.5 P3 进展（一）：`glassOverrides` 的接线对账守卫

`glassOverrides` 这层开关有**两个各自独立的真相来源**：

| 来源 | 是什么 |
|---|---|
| 运行时数据 | `lib/settings-schema.js` 的 `DEFAULTS.glassOverrides`（哪些面 × 参数默认启用） |
| 代码接线 | `src/effects.js` 里 `glassValue("面","参数",…)` 的**调用点**（源码文本） |

两者不一致就是漂移，而且是三种都不报错的形态：

- **登记了却没接线** ⇒ 开关是死的（用户打开它没有任何效果）；
- **接线了却没登记** ⇒ 开关关不掉（永远读私有值）；
- **面名拼错** ⇒ 那一项永远读到 `undefined`（静默失效）。

因此 `verify-glass-surfaces` 增第 ④ 组：从这两个来源各自提取集合，**逐面 + 逐参数**对账，
并断言每个面名都被登记表认识。

**判据有牙的证据**（注入式扰动，跑完即清）：

| 扰动 | 结果 |
|---|---|
| `drop-wire`（接线侧删一个面） | 判红 2 条：`sidebar`、"声明了没接线"逐参数列出 |
| `drop-declare`（声明侧删一个面） | 判红 1 条：`sidebar` 开关关不掉 |
| `bad-name`（塞未登记面名） | 判红 3 条：含"面名不被登记表认识" |
| 不设扰动 | 全绿 |

### 4.6 P3 进展（二）：按面变量间接层——**试过、不成立、已撤回**

为让"设置窗口"这类**与全局共用同一批 CSS 变量**的面也能独立，P3 试过一条自然的路：

> 在共享规则里插一层变量名 —— CSS 读 `var(--we-<面>-<x>, <原全局表达式>)`，
> JS 在 `applyEffects` 里写出 `--we-<面>-<x>`。

默认档下它与全局逐字节同值，所以等价性探针**通过了**（既有 33 个变量零变化、
新增 8 个全属按面层、开关可双向翻转）。**但两条既有判据当场判红**：

| 判据 | 它要求什么 | 为何必然冲突 |
|---|---|---|
| `verify-readability` **F2a** | 面纱值必须以 `var(--we-readability-base)` / `var(--we-chat-readability-base)` **开头** | 正则用 `^` + `\s+` 锚定；把 base 换成按面变量就是换掉了开头 |
| `verify-softrender` **E2** | `@supports` 回退配方与 `data-we-glass-fallback` 配方**逐字共享** | 同一段 CSS 在两处的间接化写法稍有出入，文本就不再逐字相同 |

这两条不是"顺手写的文本断言"——**它们的固定性正是防判据退化成恒真的手段**
（`hasVeil` 的锚定挡住"值里随便出现个变量就算带下限"；E2 的逐字共享挡住
"回退配方悄悄与主配方分叉"）。为给新结构让路而放宽它们，等于用结构收益换判据的牙。

> **结论（这是本次重构最重要的边界发现）**：
> **按面独立只能靠"改全局变量的取值来源"，不能靠在共享规则里插入一层变量名。**
> 前者是侧栏那条已在 P2 走通的路（自己的变量 + 解析器）；
> 后者会与可读性契约的文本形状**结构性冲突**，而那个形状是被两条判据钉住的。

**撤回内容**（全部撤净，不留死码）：CSS 的 43 处间接化、`effects.js` 的按面写点、
schema 的 4 个 `settingsWindow*` 键与对应的 `glassOverrides.settingsWindow` 声明、
golden 夹具里的 4 个新键、守卫里守这条的判据组。

**顺带记事**：撤回时我在守卫里留了那个纯函数想"以后可能用得上"，
`verify-dead-declarations`（软档）**立刻判红**——「独立脚本面零引用顶层声明」。
那条判据是对的：没有使用方的声明就是死码。已删除，只在原地留一段说明。

### 4.7 P3-c 的定性：为什么"其余面补独立控制"不是小改动

§4.6 只说了"插一层变量名会踩判据"。为了知道**到底能做什么**，我做了一次**枚举式审计**：
把所有守卫里**硬编码的 CSS 片段字面量**抽出来，与釉层变量取交集，得到"动它就会踩判据"的清单。

结论：**几乎每个釉层变量都被锁住**。

| 变量 | 被什么锁住 |
|---|---|
| `--we-blur` · `--we-glass-alpha` | `verify-client` 里以**整串字面量**出现（`"--we-blur"` 等） |
| `--we-saturate` | `verify-glass-compositing` 的 G5 配方字面量（`backdrop-filter:blur(var(--we-blur, 16px)) saturate(var(--we-saturate, 1.8));`） |
| `--we-surface-tint-light` / `-dark` | `verify-softrender` E2 的两条 recipe 字面量 |
| `--we-readability-base` | `verify-readability` F2a 的 `var(--we-readability-base)` |
| `--we-readability-floor` | F1c/F1e 的**组合形态**字面量（`calc(var(--we-readability-floor-base) * var(--we-glass-fidelity, …)`） |
| `--we-content-surface-*` | `verify-softrender` / `verify-readability` 的配方字面量 |

**唯一"自由"的是 `--we-glass-brightness` 与两个 `--we-surface-tint-rgb-*`**（恰好我的
`verify-glass-surfaces` 只按前缀提及它们，不锁字面量）。而"独立控制"若只覆盖这三个，
语义上是残的。

> **因此 P3-c 的正确定性是**：给其余面补独立控制 ≠ 加接线，而是
> **把那些面的变量从共享规则里拆出来**，而那必然改写被字面量锚定的那几条既有判据
> （F2a / F1e / G5 / E2 / verify-client 的整串断言）。
> 那是**独立的一大步**，且属于"改判据语义"——本仓纪律要求那种改动要么有充分理由、
> 要么换一条更语义化的判据（例如让 F2a 解析别名链后再断言，而不是匹配文本前缀）。
> 在没拿到那个决策之前不动它。

### 4.8 P4（一）：清理死变量 `--we-sidebar-alpha`

P0 的登记表实测：该变量在整份样式表里**精确出现 1 次、且那次在注释里**，零 CSS 消费者；
它只被 JS 用来算出 `--we-sidebar-sheen`（12 处消费）与 `--we-sidebar-tint`（6 处消费）。
⇒ 删除它的 `setProperty` 与 `removeProperty`（两个真正接线的下游照旧写出）。

**同时撤掉了一条守着它的断言**。`test/verify-client.mjs` 里有一条

```
assert.equal(typeof p['--we-sidebar-alpha'], 'string', 'sidebar alpha variable must remain available');
```

它守的是**一个没人读的变量必须继续存在** —— 正是 [`adr/0007`](../adr/0007-machine-checks-target-code-not-prose.md)
第 4 问说的"判据站在修复的对立面"。所以随实现一并撤除，并把替代断言指向真接线点
（`--we-sidebar-sheen` / `--we-sidebar-tint`）。

**防复活**：`verify-glass-surfaces` 第 ③ 组加了一条负向判据 —— 已清理的死变量**不得在样式表里
重新被消费**（`var(--x` 形式）；写在注释里说明"这里为什么不再写它"是**允许**的
（负对照专门钉住这一点：朴素正则不认注释，判定前必须先剥注释——这是我第一版负对照
写错的地方，实测踩到）。

### 4.9 P4（二）：把 §3.2 的「同源不变量」从文档落成判据

§3.2 那条不变量（"某个面用它自己的保真度 `f_s` 时，釉色混合系数与下限覆盖度必须用同一个 `f_s`"）
在本次重构里**被反复引用，却从未落地成判据**。本轮补上，`verify-glass-surfaces` 第 ⑤ 组。

它的机制是两处、四对声明：

| | 釉色（tint）侧 | 地板（floor）侧 |
|---|---|---|
| **全局** | `weClampSurfaceColor(色, 主题, glassFidelity)` → `--we-surface-tint-*` | `--we-readability-floor: calc(base * var(--we-glass-fidelity, 1))` |
| **对话栏框架** | `weClampSurfaceColor(色, 主题, chatGlassFidelity)` → `--we-chat-surface-tint-*` | `--we-chat-readability-floor: calc(base * var(--we-chat-glass-fidelity, 1))` |

判据三条：**两对各自的钳制侧与地板侧都取得到**（防空转）· **每对的地板只引用自己的 fidelity**
· **两对之间不串线**。

> ⚠️ **判据自身收紧过一次，值得记下来**：第一版写成"并集里含目标 fidelity"。
> 扰动自证时发现它**抓不住局部漂移** —— 浅 / 深两个主题块各有一条 floor 声明，
> 只把其中一条接到另一对的 fidelity 上时，另一条会把并集"补"成合格，判据照样绿。
> 改成**逐条声明检查外来变量**后才真的抓住。这条经验与 §4.6 同源：
> **凡是"在某集合里存在即可"的写法，都要先问它会不会被集合的其他成员掩盖。**

**扰动自证的记录**（`.test-cache/mutate-fidelity-crosswire.mjs`，只读、把副本改坏后验判据）：

| 情形 | 结果 |
|---|---|
| 干净源码 | 第 ⑤ 组全绿（31 项判据） |
| 把一处 floor 接到另一对的 fidelity | 判红 2 条：`同源失败=[global]` + `串线=[--we-readability-floor ← --we-chat-glass-fidelity]` |

### 4.10 P3-c 的真正阻塞点：**参数值语义不统一**（不是接线问题）

§4.7 说"其余面补独立控制要改共享规则"。本轮进一步查证后发现**更根本的一层**，
而且它连**侧栏**这个"已经独立"的面也一起卡住。

`glassOverrides.sidebar` 现在声明了三个参数为 `true`，但要让它**可关**（即真的能继承全局），
得先回答"关掉之后侧栏读全局的那个值意味着什么"。实测三个参数的答案都不一样：

| 参数 | 全局那套 | 侧栏那套 | 能否直接互换 |
|---|---|---|---|
| **模糊** | `blur` px（KINDS 0–60，UI 0–60），直接输出 | `sidebarBlur` px（KINDS 0–200，UI 0–60），直接输出 | ✅ **可以**——两者都是"值 + px"、无曲线，交集 0–60 逐点等价 |
| **颜色** | `glassColor` → `--we-surface-tint-*`（经保真度钳制） | `sidebarColor` → `--we-sidebar-color`（**不经钳制**，另有 `--we-sidebar-tint` 权重） | ⚠️ 语义不同（钳制与否），换过去会改观感 |
| **透明度** | `glassAlpha` 0–60 → `max(0.10, 0.25 − x/60×0.15)`，值域 **0.10–0.25** | `sidebarAlpha` 0–200 → `max(0.015, 0.32 − x/200×0.305)`，值域 **0.015–0.32** | ❌ **不可能** |

**透明度这一项是硬的**，而且比"量纲差"更彻底：

> 两条曲线的**值域都不同**（0.015–0.32 vs 0.10–0.25），所以**不存在任何因子或仿射
> 重映射**能让它们逐点相等 —— 侧栏能去到 0.015（近乎全透），全局最低只到 0.10。
> 已用逐点枚举证伪了 `×0.3` 这类归一化（61/61 处不一致），
> 也证伪了"乘个系数再对齐曲线"（见 `.test-cache/verify-alpha-normalization.mjs`
> 与 `verify-alpha-migration.mjs`）。

而且它的下游有**两处都按旧量纲算**，任何来源切换都会同时跳变：

```
sidebarAlphaPct ──┬─→ sidebarAlpha = max(0.015, 0.32 − pct/200×0.305) ─→ --we-sidebar-sheen（12 处消费）
                  └─→ sidebarTint  = 20 + (200 − pct)/200 × 28           ─→ --we-sidebar-tint（6 处消费）
```

> **结论**：让侧栏透明度"可继承"不是接线工作，而是**参数值语义的迁移** ——
> 必须把"透明度"定义成一个**与面无关的比值**，各面再各自映射到自己的观感曲线。
> 而这三种收口都会**改变侧栏观感**：
> (a) 直接转换量纲、(b) 参数值语义化（比值 + 每面曲线）、(c) 加设置版本标记区分新旧值。
> 它们都与本方案 §1.4 的硬约束"**默认逐位不变**"冲突。
>
> **因此 P3-c 在拿到"是否允许侧栏观感发生一次迁移"这个决定之前无法推进。**
> 这是一个**被证实的阻塞点**，不是未尝试的猜测。
>
> ✅ **用户已裁决（授权一次语义迁移），本条已落地** —— 见 §4.12。上面这段分析保留不改：
> "为什么阻塞"与"后来怎么解的"都有价值，而**结论是走 (b) 参数值语义化**。

**附：模糊那一项其实已经可用**（唯一一个）。若把 `glassOverrides.sidebar.blur` 设为 `false`，
侧栏会读全局 `blur`（0–60），与侧栏自己的 `sidebarBlur` 在 UI 可及范围内逐点等价。
但它**今天默认是 `true`**，改成 `false` 反而会让"两值不同的用户"观感跳变 ——
所以这个能力已经就位，只是默认档不该动它。这也说明模型本身是通的：
**卡住的从来不是"读谁"的机制，而是"两边的值是不是同一种东西"**。

### 4.11 P4（四）：golden 夹具的**键集快照**判据

**为什么补**：夹具 `test/fixtures/settings-sanitize-golden.json` 的**值**由 `verify-client`
逐用例回放比对（`canon(sanitizeFromSchema(input))` vs `canon(want)`）。那是**回放**，
**不覆盖键的存在性** —— 夹具里某个对象少一个键时，值比对照样全过，守卫**照样绿**。
而夹具同步一直靠 note 里的人工约定（"新键按引入时行为补入"）。

**这不是理论风险**：本目标实施期间**已真实发生两次** —— 加 `glassOverrides`、
加设置窗口那批键时，都是"改完 schema 忘了同步夹具 → `verify` 红 → 再写一次性脚本补"。

**判据口径（两次修正后）**：以夹具**自身**每个用例的键集为快照，断言逐用例一致。

判据写对之前踩了两个坑，都是"我以为知道形状"造成的：

| 第一版 | 现象 | 真相 |

| 应有键集 = `KINDS` 减 `CLIENT_ONLY` | 报 9 个"缺键" | 我**手抄**了 `sanitizeFromSchema` 的筛选规则，漏了 `FONTSET_KEYS` / `DEFAULTS_ONLY` 两条 ⇒ 改成**调用真函数**取键集 |
| 应有键集 = `sanitizeFromSchema({}, side)` | 仍报 3 个"缺键" + 2 个"多键" | 实测否掉了这个前提：`glassFidelity` / `chatGlassFidelity` / `themeFollow` **只在 host 侧**出现；`rotationInterval` / `sceneFrameUrl` 只在**非对象输入**那 3 个用例的 client 侧出现 ⇒ 改成**快照口径** |

最后把 `rotationInterval` / `sceneFrameUrl` 显式列为"逐用例可变键"并**写明为什么可以排除**
（它们不是"新增键漏补"的对象，且它们**值**另有逐用例值比对管着）。

**扰动自证**（`.test-cache/mutate-fixture-keys.mjs`，只读、在副本上做）：

### 4.12 P3-c 的落地：参数值语义化（用户已授权一次语义迁移）

**做法**：把"控件的**归一化位置**"（0–1）作为**与面无关的参数值**，每个面再用自己的量程
把它展开。于是"继承"有了确定含义：

> **全局滑杆的半程 = 本面滑杆的半程**（各自量程的同一比例位置），而**不是同一个数字**。

实现只有一处、三条接线（`src/effects.js`）：

```
norm(v, max)   = clamp01(v / max)                     归一化位置
denorm(t, max) = t * max                              本面表达值
侧栏模糊     : glassValue("sidebar","blur",         norm(sidebarBlur,200),        norm(blur,60))              → denorm(_, 200)
侧栏透明度   : glassValue("sidebar","transparency", norm(sidebarAlpha,200),      norm(glassAlpha,60))        → denorm(_, 200)
内容面透明度 : glassValue("sidebarContent","transparency", norm(sidebarContentAlpha,80), norm(glassAlpha,60)) → denorm(_, 80)
```

**逐项量程**（实测三处都不一样，所以归一化必须**逐面用自己那个数**）：

| 参数 | 全局键 / 量程 | 本面键 / 量程 |
|---|---|---|
| 模糊 | `blur` / 0–60 | `sidebarBlur` / **0–200** |
| 透明度 | `glassAlpha` / 0–60 | `sidebarAlpha` / **0–200** |
| 内容面透明度 | `glassAlpha` / 0–60 | `sidebarContentAlpha` / **0–80** |

**默认档仍逐位不变**（等价性探针：既有 33 个变量零变化）—— 因为 `norm(x,max)·max === x`。
**开关关掉后**的行为才有意改变：全局 `blur=33`（量程 0.55）现在让侧栏得到 `110px`（量程 0.55），
而**不是**把 33 直接当 200 分制用（那是修复前的错配）。

**判据**（守卫第 ⑦ 组）：`glassValue` 的取值槽位**不允许裸键**，必须是 `norm(…)`；
量纲无关的参数（颜色 —— 它的"继承"就是"改用全局那个色"，且带 `""` 哨兵）**必须登记**在
`SCALE_FREE_PARAMS` 里才豁免。

且漏了左侧栏与插件浮层。现在按实测覆盖面重写。

> **教训**：我给这项改名时，依据是"`--we-blur` 主要在对话栏规则里"这个**印象**，
> 而不是逐条归面。覆盖面这种事**必须机器枚举** —— 正是本方案 §6 反复强调的那条。
> 而你一眼指出"侧边栏也生效"，那时我手里其实已经有能证明它的工具。

**(b) 判据设计上的一个漏检：颜色是靠"恰好没写 `norm()`"通过检查的。**

第 ⑦ 组判据第一版要求"每个槽位必须 `norm(…)` 或字符串字面量"。颜色参数传的是裸键
（`selection.sidebarColor`），本应被判出 —— 但它的写法恰好让判据放过了它，
于是**凡与量纲相关的裸键都会被同一个漏洞放过**。那不是判据，是巧合。

修法：把"量纲无关"从**隐式漏检**改成**显式登记**（`SCALE_FREE_PARAMS = {color}`），
并要求"零参 `norm()` 占位"也必须登记（`NORM_FREE_KEYS`，当前空集）——
后门必须被堵住，否则加新面时写个零参占位就能绕过全部量纲检查。

### 4.14 剩余接线的取证：修正 §4.7 的过度结论

§4.7 从"字面量审计"得出"几乎每个釉层变量都被判据锁住"。**那个结论有一部分是错的** ——
审计脚本把 `console.log(...)` 里的字符串和注释也当成了"判据锚定"。做了一次
**只收判据实参**（`assert.*` / `check(` 那一行）的复审，结论**大幅反转**：

| 变量 | 真正的判据锚定 | 能否逐面间接化 |
|---|---|---|
| `--we-glass-alpha` | **无** | ✅ 可以 |
| `--we-glass-brightness` | **无** | ✅ 可以 |
| `--we-surface-tint-rgb-*` | **无** | ✅ 可以 |
| `--we-content-surface-alpha` / `-color` | **无** | ✅ 可以 |
| `--we-surface-tint-light` / `-dark` | 仅 E2 的 4 条**配方文本** | ✅ 可以（只要不动那 4 条配方所在的规则） |
| `--we-blur` | G5 的 `readsBoth = /var\(--we-blur\b/` | ✅ **可以** —— 它是**子串存在**判定，`var(--we-设置窗口-blur, var(--we-blur, 16px))` 照样含 `var(--we-blur` |
| `--we-saturate` | 同 G5 + D1 | ✅ 可以（同上理由） |
| **`--we-readability-floor`** | **F1c 锚 `body { }` 里那条声明的形态** | ❌ **不可以** |
| **`--we-readability-base`** | **F2a 的 `^` 锚定面纱形** + F1c | ❌ **不可以** |

**两条硬约束（逐字）**：

- **F2a** 的面纱判据要求声明**以**
  `color-mix(in srgb, var(--we-readability-base) calc(var(--we-readability-floor) * 100%),`
  **开头**（只认 `--we-readability-*` 或 `--we-chat-readability-*` 两种字面形，见 `(?:chat-)?`）。
- **F1c** 要求 `body { }` / `body[data-ds-dark-theme] { }` 里那条
  `--we-readability-floor: calc(var(--we-readability-floor-base) * var(--we-glass-fidelity, 1));` **原样在**。

⇒ **结论（修正 §4.7）**：

> **逐面独立的可行范围是「颜色 / 透明度 / 模糊 / 亮度」四项；「保真度」与下限覆盖度
> 不能逐面独立** —— 任何面只要用**共享**的面纱声明，它的地板就只能来自全局那对变量。
> 而"保真度"恰恰是**颜色 vs 可读性**的权衡旋钮，所以对共享面纱的面来说，
> **逐面保真度在"判据不变"的前提下不可达**。

**对 UI 的直接影响**：「设置窗口玻璃·独立配置」/「浮层玻璃·独立配置」/「左侧栏玻璃·独立配置」
**不应包含「玻璃保真度」**（给了也接不通，会变成第二个"开关是死的"）。
**「对话框玻璃·独立配置」可以保留它** —— 对话栏那一族有**自己的** `--we-chat-readability-*`
（上游为它单独拆过一把尺），而 F2a 的面纱形**明确接受** `--we-chat-` 前缀。

> 在它右边的"结果"列与对应的实施记录里 —— 好几处与当时的预判**不同**，那些差异本身是产出。

| # | 任务 | 当时的做法/风险 | 结果 |
|---|---|---|---|

| **W2** | 设置窗口：4 个变量逐面化 | 中 | ✅ 但只做了 **2 项**（模糊/透明度）：另 2 项不是可配置参数 §4.17 |

也必须先取证"这条教训的现场）：

> **W5 才是真正的大头**：今天这些子面**没有"关"这个状态** —— 它们从壁纸激活起就一直吃玻璃配方。
> 要实现"关 ⇒ 原生不透明纯色"，等于给每个面补一套**回退样式**……这是**逐面**的视觉对齐工作。

**实际是**：这些面的规则**本来就挂在一个 body 属性锚点上**（`data-we-glass-window` /
`data-we-left-sidebar`），属性摘掉 ⇒ 规则组不匹配 ⇒ **原生样式自然生效**。
所以 W5 的工作量是"给该面的规则组加一个统一前缀"，**不是**"写回退样式"。
只有 `conversation` / `floaters` 需要**新增**锚点（各 ~6 行选择器改动）。


**建议顺序**：**W6**（零风险，先把"给不了的东西"从 UI 撤掉，避免承诺做不到的旋钮）→
**W1**（让开关真的有牙）→ **W2 / W3 / W4**（逐面接线，每次只做一个面并跑全链）→
**W5**（最后做，且**先只做一个面**验证回退样式的形态，再推广）。

**为什么不能一次做完**：W2–W4 每一面都要改"被判据以子串/配方形式看着"的规则，
一次改三个面会让 `verify:all` 的失败信息混在一起、无法定位是哪一面的哪条判据翻了。

### 4.16 W1 的实施记录：把「开关状态」与「能力声明」拆成两个键

**发现的根因（一个键担两个职责）**：`glassOverrides[面][参数]` 同时被用作
① 用户的"独立配置开关"、② "这一面的这个参数有独立值可取"的声明。后果是
**开关读数与实际行为不一致**：`conversation` 只声明了两个参数，而开关读数要求
"各项全 true" ⇒ 它读作**关**，但 `glassValue` 却因为 flag 在而**真的走 profile 支**。

**改法（两个键各管一件事）**：

| 键 | 语义 | 默认 |
|---|---|---|
| `glassIndependent[面]` | **用户开关**（"这一面用自己那套"） | 既有面 `true` · 新增子项 `false` |
| `glassOverrides[面][参数]` | **已接线**的能力声明（守卫第 ④ 组拒绝"声明了没接线"） | 按接线进度逐面补 |

取值口径随之变成**"与"**：`glassIndependent[面] === true` **且** 该参数已声明，才读自己的值。

**⚠️ 这一步差点造成一次静默观感回归，等价性探针当场抓到**：

加了"与"门之后，`sidebar` / `sidebarContent` 因为**没有** `glassIndependent` 条目而默认"关"
⇒ 它们**静默退化成继承全局**。实测 5 个变量同时改变，例如
`--we-sidebar-blur` 从 `16px` 变成 `norm(16,60)×200 = 53.33px`。

**根因**：`sidebar` / `sidebarContent` 从 P2 起就读自己的键 —— 那时还没有"独立配置开关"
这一层。把它们纳入新键时，**默认值必须是 `true`**（迁就既有事实），
而「玻璃 UI」那三个子项是**新增能力**、默认 `false`。

修法是把默认值收进一张**权威表**、在 schema 里导出，UI 默认值与守卫用**同一个表**：

```js
const GLASS_INDEPENDENT_DEFAULTS = {
  sidebar: true, sidebarContent: true,          // 既有独立面（P2 起就独立读值）
  settingsWindow: false, conversation: false, floaters: false,   // 新增能力：默认继承全局
};
```

**判据（守卫第 ⑧ 组，3 条 + 2 条负对照）**：

1. 开关读数**只看** `glassIndependent`、翻开关**只写**它、`glassValue` 要求"开关 ∧ 已声明"；
2. 每个已接线的子项都有能力行（"开关开了却读不到自己的值"要被拦下）；
3. 独立开关默认值与**权威表逐面一致**（既有面误设成关 / 漏面都判红）。

> **这条回归值得记一笔**：它是"把既有行为纳入新开关层"时的**默认值陷阱** ——
> 新层的默认值若取"新能力的直觉默认（关）"，就会**静默改掉既有行为**。
> 当时 `verify:all` 是**绿的**（没有任何判据盯着"侧栏默认该读自己的值"这个**事实**），
> 唯一发现它的是等价性探针。

### 4.17 W2 的实施记录：设置窗口的模糊 + 透明度接通

**范围（按 §4.14 的取证裁剪）**：这一面**只能做两项**，所以只做两项。

| 项 | 结论 | 理由 |
|---|---|---|
| 模糊 | ✅ 接通 | G5 的 `readsBoth` 是**子串判定**，内层 `var(--we-blur, 16px)` 保留即通过 |
| 透明度 | ✅ 接通 | `--we-glass-alpha` **无判据锚定** |
| 饱和度 / 亮度 | ⚪ **不纳入** | 它们**不是可配置参数**（全局 `--we-saturate` 是常量 `GLASS_SATURATE`、brightness 在本面被钉在 1.04）⇒ 纳入会给出登记表里不存在的旋钮 |
| 保真度 / 地板 | ❌ **不可达** | F2a 面纱形 + F1c 声明形（§4.14）⇒ 本面没有 `settingsWindowFidelity` |

**CSS 侧**（`src/styles.js`，该面的 **4 条规则**：浅/深 + `@supports` 回退里的浅/深）：

```
--we-glass-alpha, 0.5   →  --we-settings-window-alpha, var(--we-glass-alpha, 0.5)      ×6
var(--we-blur, 16px)    →  var(--we-settings-window-blur, var(--we-blur, 16px))         ×2
```

**JS 侧**（`src/effects.js`）：只在**开关开且该参数已声明**时写那两个变量；
默认档**完全不写** ⇒ CSS 走内层全局兜底 ⇒ 与接线前逐位一致。

**自证**（`.test-cache/w2-prove-wired.mjs`）：

| 场景 | `--we-settings-window-blur` | `--we-settings-window-alpha` |
|---|---|---|
| 开关关（默认） | `undefined`（走全局兜底） | `undefined` |
| 开独立（33px / 55%） | `"33px"` | `"0.1125"`（= `max(0.10, 0.25 − 55/60×0.15)`） |

**判据侧的一个自我修正（第 ⑦ 组）**：这两项的**两侧量程本来就相同**（0–60 = 0–60），
套 `norm()` 是多余的。于是给守卫加了第二类豁免，但**第一版按参数名豁免**，
把 `sidebar.blur`（本面 0–200 对全局 0–60，**确实需要**归一化）也一起放过了 ——
覆盖面判据当场报"需归一化的槽位变成 0"。

> ⇒ 改成按 **`面.参数`** 登记（`SAME_SCALE_PARAMS = {'settingsWindow.blur', 'settingsWindow.transparency'}`）。
> **这是判据自己把设计错误逼出来的**：豁免的粒度必须与"两侧量程是否一致"这个事实的粒度对齐 ——
> 那是**面 × 参数**，不是参数。

### 4.18 W3 的实施记录：左侧栏覆盖（乙类）的模糊 + 透明度接通

**范围**：这一面共 6 条规则，但可接线的只有 **4 个消费点**（浅/深各一对）：

| 变量 | 结论 | 理由 |
|---|---|---|
| `--we-blur` | ✅ 接通（×2） | G5 子串判定，内层兜底保留即通过 |
| `--we-glass-alpha` | ✅ 接通（×2） | 无判据锚定 |
| `--we-saturate` / `--we-glass-brightness` | ⚪ 不纳入 | **非可配置参数**（常量） |
| `--we-surface-tint-light/dark` | ⚠️ **不纳入** | 其中 `--dsw-alias-bg-layer-1: var(--we-surface-tint-light, #ffffff)` 正是 **E2 的配方文本** |
| `--we-readability-floor/base` | ❌ 不可达 | F1c 声明形 + F2a 面纱形 |

**CSS 侧**（该面 2 条规则）：

```
--we-glass-alpha, 0.5  →  --we-left-sidebar-alpha, var(--we-glass-alpha, 0.5)   ×2
var(--we-blur, 16px)   →  var(--we-left-sidebar-blur, var(--we-blur, 16px))      ×2
```

**门控是"两个门"（乙类的特征）**：只开「左侧栏覆盖」（`leftSidebarGlass`）时它**仍走全局兜底**；
还要再开耦合在它下面的「左侧栏玻璃·独立配置」（`glassIndependent.leftSidebar`）才读自己的值。

**自证**（`.test-cache/w3-prove-wired.mjs`）：

| 场景 | `--we-left-sidebar-blur` | `--we-left-sidebar-alpha` |
|---|---|---|
| 覆盖关 | `undefined` | `undefined` |
| 只开覆盖（独立关） | `undefined`（走全局兜底） | `undefined` |
| 两门齐开（33px / 55%） | `"33px"` | `"0.1125"` |

**一个结构问题与它的解法**：W6 曾把 `leftSidebar` 从 `GLASS_CHILDREN` 里**删掉**（因为它是乙类、
不该出现在「玻璃 UI」里），结果它的三个键（`leftSidebarBlur` / `leftSidebarTransparency` /
`leftSidebarColor`）在 schema 里**不存在** ⇒ 接线的变量永远走兜底。

解法是**把它放回登记表、但加 `panelOff: true`** —— 登记表同时充当"键生成器"与"面板清单"，
两者本就该分开：

```js
{ id: 'leftSidebar', …, panelOff: true, params: { color: 0, transparency: 60, blur: 60 } }
```

面板 `.filter((c) => !c.panelOff)`；而 `glassChildren` / `glassIndependent` 的默认值也按同一过滤
生成 ⇒ **它不参与「子 UI 玻璃」那一层**（否则就有两个开关控同一件事），
但它的键照常生成。**登记表的重载职责由此显式化**，不再靠"删掉它"来表达"不进面板"。

### 4.19 W4 的实施记录：插件自身浮层的模糊 + 透明度接通

**我先前的预判是错的**。§4.15 的消费矩阵只显示了 `--we-surface-tint-light` 1 处，我据此预告
"这一面几乎没有可接线的变量"。逐规则取证后发现**它可以接线**：

| 规则 | 可接线 | 不可动 |
|---|---|---|
| `.we-update-notice` | `--we-blur`×2 · `--we-glass-alpha`×1 | `--we-readability-*`（F1c/F2a）· `--we-surface-tint-light`（E2 配方） |
| `.we-repo-panel--open` | `--we-blur`×2 · `--we-glass-alpha`×1 | 同上 + `--we-saturate`/`--we-glass-brightness`（常量） |

**矩阵为什么漏了它**：那张矩阵按**顶层规则**归面，而 `.we-update-notice` / `.we-repo-panel--open`
的后备过滤链没能把它们的 `--we-blur` 归到本面 —— 是**归面口径**的问题，不是"这一面没有变量"。
⇒ 教训：**"某面没有可接线变量"这种结论必须逐规则核对**，不能只看一张聚合表。

**CSS**：

```
--we-glass-alpha, 0.5  →  --we-floaters-alpha, var(--we-glass-alpha, 0.5)   ×2
var(--we-blur, 16px)   →  var(--we-floaters-blur, var(--we-blur, 16px))      ×4（更新提示 + 仓库抽屉各 ×2）
```

**自证**（`.test-cache/w4-prove-wired.mjs`）：独立关 ⇒ 两个变量都不写；
开独立（33px / 55%）⇒ `--we-floaters-blur = "33px"`、`--we-floaters-alpha = "0.1125"`。

**顺带修掉一条写反的判据**：第 ⑧ 组的"每个已接线的子项都有能力行"原本写成
`childWithNoCap.length > 0`（**要求至少有一个子项还缺能力行**）—— 那是我在 W2/W4 未接完的
过渡期写的，**方向是反的**：全部接完之后它反而判红。现在改成正确的不变量
"**不允许**有已接线却缺能力行的子项"。

| 面 | 已接线参数 | 门控 |
|---|---|---|

| `conversation`（对话框玻璃） | color · fidelity | `glassIndependent.conversation` |

### 4.21 W5 的实施记录（第一个面）：设置窗口的"关 ⇒ 回原生"

**先取证再动手**。探针（`.test-cache/w5-delta-probe.mjs`）比对 `glassWindow` 开/关两种状态，
结论很关键：

> **差异只有 1 个 body 属性，0 个变量差异。**

也就是说：这些面"吃不吃玻璃"在今天的表达方式**就是一个属性** —— 属性在，那一组规则生效；
属性摘掉，规则整组不生效，**原生样式自然生效**（CSS 层叠，不需要"撤销"什么）。

⇒ **W5 在本面不需要另写回退样式**，只需要把"子 UI 玻璃关"落到**同一个属性**上：

```js
const settingsWindowGlassOn = !!selection.glassWindow
  && !(selection.glassChildren && selection.glassChildren.settingsWindow === false);
if (settingsWindowGlassOn) document.body.setAttribute("data-we-glass-window", "on");
else document.body.removeAttribute("data-we-glass-window");
```

**自证**（`.test-cache/w5-prove-fallback.mjs`，4 个场景全过）：

| 场景 | `data-we-glass-window` |
|---|---|
| 默认（两级都开） | `"on"` |
| **子项玻璃关** ⇒ 回到原生 | `undefined` |
| `glassWindow` 关 | `undefined` |
| 子项玻璃显式 `true` | `"on"` |

> **这修正了我在 §4.15 里对 W5 的风险估计（"高"）**。我当时以为要"逐面补一套回退样式"，
> 但那个判断建立在"这些面没有关态、所以得手写回退"的假设上 —— 取证后发现它们**本来就有**
> 一个干净的关态机制（body 属性 + 属性门控的规则组），W5 只是把新的开关**接到同一个属性**上。
> 教训与 §4.19 同源：**风险估计也必须先取证**，否则会把小改动误报成大工程。

**⚠️ 一处已知的语义重叠（记账，待裁决）**：本面因此有**两个**开关都能到"原生"——
「设置窗口液态玻璃」（`glassWindow`）与「子 UI 玻璃 → 设置窗口玻璃」（`glassChildren.settingsWindow`）。
保留两者是因为「子 UI 玻璃」那一层的**总开关必须对所有子项生效**；
重叠的代价是**一处 UI 不一致**：把子项关掉后，「设置窗口液态玻璃」那个开关仍显示为开，
但实际已回原生。

> ✅ **已结（§10.20）**：重叠的两个开关**都退役了** —— `glassWindow` 删除（功能由「设置窗口玻璃·独立配置」
> 接管），`glassChildren` 整层删除（那个"关"并不能如愿回到原生纯色）。本面现在恒吃玻璃，
> 于是这处 UI 不一致在结构上不可能再出现。

**其余三个面待推广**，各自的原生机制不同（`leftSidebar` 有自己的 `leftSidebarGlass` +
属性；`conversation` / `floaters` 今天**没有**属性门控，是直接吃全局变量 ⇒ 它们的"关"需要
新增落点，风险确实较高）。**这正是"先只做一个面"的价值** —— 它证明了"关"可以用属性表达，
但也暴露了"有属性门控的面"与"没有属性门控的面"难度不同。

### 4.22 W5 推广：逐面的门控覆盖率取证 + 判据（第 ⑨ 组）

**取证方式**：对每个面，取它全部的**成员规则**（按选择器），再看其中有多少条**不带锚点**。
"不带锚点"= 属性摘掉后它仍然生效 ⇒ **回退不干净**。

| 面 | 成员规则 | 不带锚点 | 结论 |
|---|---|---|---|
| 设置窗口 | 6 | **0** | ✅ 门控完整（W5 已做，§4.21） |
| 左侧栏覆盖 | 8 | **0** | ✅ **门控本来就完整** ⇒ W5 对它**无需改动** |
| 对话栏 | 4 | **0**（锚点 `data-we-glass-fallback` 的那条除外，见下） | ⚠️ 接近可做 |
| 插件浮层 | 16 | **14** | ❌ 今天完全没有"关"的落点 |

**两个重要澄清**：

1. **左侧栏覆盖的 W5 已经成立** —— 它那 8 条规则**全部**挂在 `data-we-left-sidebar` 上，
   而那个属性由 `leftSidebarGlass`（「左侧栏覆盖」）控制。所以"关 ⇒ 回原生"**今天就是对的**，
   W5 对它没有待办。
2. **对话栏的锚点是 `data-we-wallpaper`**，不是 `data-we-glass-window` —— 即它的玻璃
   **随壁纸激活即生效**，没有独立的"关"。它已有一条 `data-we-glass-fallback` 的回退规则，
   方向对，但那只覆盖 `::before` 一条。

**⇒ W5 的真实剩余范围**：**对话栏**与**插件浮层**需要**新增门控属性**（例如
`data-we-glass-chat` / `data-we-glass-floaters`）并把各自的玻璃规则组挂上去。
这不是"写撤销样式"，而是"给规则组加一个统一的前缀" —— 与既有 8 个 body 属性同一机制。

**判据（守卫第 ⑨ 组，3 条 + 1 条负对照）**：把上表的"成员规则 × 锚点"做成机器检查：

- 已完成 W5 的面：`ungated.length === 0`（**回退必须干净**）；
- 覆盖面：登记的面都真的取到了规则（防判据空转）；
- **未完成 W5 的面必须显式登记**（`done: false` + 计数）——
  这样"哪些面回退干净、哪些没有"在判据里**可见**，而不是靠记忆。

> 这条判据的价值在于它守的是一种**浏览器里才看得见、而判据全绿**的缺陷：
> "关掉后还剩一点玻璃味"。当前输出：
> `settings-window 6/6 · left-sidebar-override 8/8`，
> 待推广：`glass-child-conversation(3) · plugin-floaters(14)`。

### 4.23 W5 收口：四个面全部完成

**判据口径修正（重要）**：第 ⑨ 组最初把"**同面的全部规则**"都算进覆盖率，

⇒ 判据收紧为 **`anchorGateCoverageGlaze`**：只统计 **body 里含 `var(--we-`** 的同类规则。
这才对得上"回退干净"的真实含义 —— 一个面的**排版规则不需要挂釉层门控**。
（若不收紧，就会逼着人给排版规则挂无意义的锚点，那是"为判据而判据"。）

**对话栏**（本轮）：三条主规则加 `[data-we-glass-chat]` 锚点（共 7 处选择器，含多选择器行）：


**浮层**（本轮）：6 条顶层浮层规则加 `[data-we-glass-floaters]` 锚点

**最终门控覆盖率**（判据输出）：

```

  settings-window 6/6 · left-sidebar-override 7/7 · glass-child-conversation 3/3 · plugin-floaters 4/4
```

**四个自证**（`w5-prove-fallback` / `w5b-prove-chat-gate` / `w5c-prove-floaters-gate`）都验证了
"子项玻璃关 ⇒ 摘属性（回原生）"与"独立开 ⇒ 才写自己的值"这两个方向。

**W5 的完整形态**（这是本方案里最后一块）：

| 面 | "关"的落点 | 谁控制 |
|---|---|---|
| 设置窗口 | `data-we-glass-window` | `glassWindow` **且** `glassChildren.settingsWindow` |
| 左侧栏覆盖 | `data-we-left-sidebar` | `leftSidebarGlass`（**本来就有**，W5 无需改动） |

| 插件浮层 | `data-we-glass-floaters` | `glassChildren.floaters` |

原生样式自然生效。这是 §4.21 学到的形态，四个面一致适用。







### 4.24 用户实测"全部子项无反应"的根因：**运行中的产物正是抛异常的那一版**

（§4.23 交付后用户实测：控件在，开关/滑杆动了**没有任何视觉变化**，且**全部子项都无反应**。）

**根因是一个运行期异常，不是接线缺失。** 证据来自宿主自己的诊断日志：
`~/.dsh-wallpaper-engine/diag/http.jsonl` 记的是**渲染进程的控制台**（`"kind":"renderer"`），
里面有 66 条 `client-error`，全是同一句：

```

    at applyEffects (…/dsh-plugin-wallpaper-engine/client.js&rev=9dbd47d9c1b7:14217:24)
```

时间分布与用户的点击对齐：09:47:34 起、末条 10:25:18，其中 10:22:02 / 10:22:53 / 10:22:57 / 10:25:18
是四次成簇的三连击（= 三次拖动）。这正是 §4.16 引入、随后于 10:20:50 修掉的 **TDZ**：
`glassValue` 的定义在使用点之后 ⇒ `applyEffects` 在玻璃取值那一段的**第一行就抛** ⇒
**其后的全部写值都不执行** ⇒ 所有玻璃面同时失效，且与"动的是哪一项"无关 ——

**为什么修完仍不生效（关键）**：磁盘上的产物 10:20:58 已重建，但日志里 **66 条消息的 `rev` 只有一个值
`9dbd47d9c1b7`**，其中还包含一个 **10:21:00（重建后 2 秒）才 boot 的上下文**。也就是说宿主给页面的是
**本次会话内缓存的那一份产物**，磁盘重建不改变它。数据目录与 Electron 缓存里也**没有**任何旧副本
（按 `glassValue` 全文搜过）。⇒ **必须整进程重启 app**；单纯刷新页面不保证生效。

**为什么会走到这一步（流程性事实，比这个 bug 本身更重要）**：
`~/.dsh/profiles/{desktop,web}/node_modules/dsh-plugin-wallpaper-engine` 是指向本工作区的
**junction**（`LinkType=Junction`，两侧同一 target）。即**我的每一次中间态构建都立刻就是"已安装的插件"**，
没有安装/复制这道缓冲。WD 期间任何一次中途 `npm run build` 都可能被正在运行的 app 取走。
守卫不可能发现这件事：**缺陷不在最终树里，而在被部署产物的一个瞬时状态里** ——
所有基于树的判据（含本方案 48 项玻璃守卫）对它天然失明。

**新工具：不需要 F12 的运行期通道。** 上述 `diag/http.jsonl` 是渲染进程控制台的全量镜像
（`client-boot` / `client-error` / `we-live` 心跳都进去），宿主侧另有 `kind:"client"` 行。
以后排查运行期问题一律读它，不必让用户开 DevTools。

**顺带查出的守卫缺口（真实，待补）**：`test/verify-client.mjs` 里那条执行型判据
（`new Function` + `with(Proxy)` 真跑 `applyEffects`）用的 `selection` 替身**不含
`glassChildren` / `glassIndependent` / `glassOverrides` / `glassFidelity`**，于是所有"按面"分支的
`if` 体从不进入 —— 它只证明"函数能跑完"，**没有**证明"按面取值真的被写出来"。
本方案关于按面变量的判据目前**全是文本判据**（第 ⑧ 组等），行为层是空的。
补法：给那份替身补上这几个键与各面 profile 值，断言按面变量**确实**出现在 `props` 里，
并配一条"开关为 false 时不得写出"的负对照。

### 4.25 真正的根因（第三层）：**默认值机制把三张表变成了死代码**

（用户重启 app 后实测：TDZ 报错消失，但"调整 UI 仍然无变化"。⇒ §4.24 那条 TDZ 是**另一个**
独立缺陷，不是"无反应"的全部原因。继续查运行期事实 —— 宿主侧的真源就能定罪。）

**证据（宿主真源，不是推断）**：`~/.dsh-wallpaper-engine/config.json`（10:39:52 刚写过）里

```json
"glassChildren": {}, "glassIndependent": {}, "glassOverrides": {}
```

而 `DEFAULTS` 里这三张表**都不是空的**（探针直接跑 schema）：

```
DEFAULTS.glassOverrides   = {sidebar:{blur,color,transparency}, sidebarContent:{...},
                             conversation:{color,fidelity}, settingsWindow:{blur,transparency},
                             leftSidebar:{...}, floaters:{...}}
DEFAULTS.glassIndependent = {sidebar:true, sidebarContent:true, settingsWindow:false, ...}
DEFAULTS.glassChildren    = {settingsWindow:true, conversation:true, floaters:true}
sanitizeFromSchema({})    = 三者全是 {}          ← 默认值被完全忽略
```

**机制（三行代码）**：`readOne()` 对每个 kind 都传了 `def`（`clampNum(v, lo, hi, def)`、
`hex → def`…），**只有两个 map 类 kind 没有**：

```js
case 'boolMapTree': return readBoolMapTree(v);   // ← def 被丢掉
case 'boolMap':     return readBoolMap(v);       // ← def 被丢掉
```

而 `readBoolMap(undefined) === {}` ⇒ 这三张表在真实会话里**恒为空**。`src/persistence.js` 的
两条路径（`:178` 宿主设置、`:187` 本地缓存）都是 `Object.assign(selection, sanitizeSettings(…))`，
**sanitize 的输出会覆盖 `{...DEFAULTS}`** ⇒ 连"新用户走 DEFAULTS 分支"这条兜底也保不住。

**后果逐条对得上用户的现象**：
1. `glassOverrides` 恒空 ⇒ `glassOverrideOn(面,参数)` **全 false** ⇒ 每个「独立配置」旋钮
   **天生不动** —— 这才是"子 UI 玻璃无一接线"的实义（接线在，取值被能力表否决）。
2. `glassIndependent` 恒空 ⇒ `glassIndependentOn()` 恒 false，第二把锁。
3. `glassChildren` 恒空 ⇒ 面板 `childOnCount = 0` ⇒ 总开关显示为关。
4. `readBoolMap` "只收 `true`、剪掉非真值" ⇒ 即使翻开关写进 `false`，**落盘即丢** ——
   而本功能的"关"正是**回原生**，那是一个必须能存住的状态。旧实现连"全关"都存不住。

**为什么 ①–⑨ 全绿却抓不到**（两条，都要记住）：
- 那九组**全是形态判据**：证明"接线写对了"，不证明"接线在真实会话里可达"。
- `test/fixtures/settings-sanitize-golden.json` 的生成方式是"**从实际输出抄一遍**" ——
  它把这三张表的 `{}` 抄成了期望（33 处，非空形态 **0** 处）。**从输出生成的夹具只会检测变化，
  对正确性没有意见**：它把缺陷钉成了契约，于是整套 sanitize 判据为这个 bug 提供了"绿灯背书"。

**修复（三处，都在 `lib/settings-schema.js`）**：
1. `glassOverrides` 改 kind `'const'`。理由就是它自己的定义：**能力声明，不是用户状态**
   （用户状态是 `glassIndependent`）。好处有二：输入里送什么都不参与取值 ⇒ **免疫已落盘的 `{}`**；
   且它随 settings 一起被写回 ⇒ 用户那份脏存档**下一次 PUT 自愈**。
2. `readBoolMap(raw, def)`：以 `def` 为起点，再用输入里的**显式布尔**（`true` 与 `false` 都算）
   覆盖。于是"缺省键取默认值"与"关得住"同时成立。
3. 旧 kind `boolMapTree` 与其读者一并删除（改 `const` 后它是死代码）。

空对象语义也随之明确：**`{}` = 全取默认值**（因为"全关"必须逐键写 `false` 才能表达）。
于是"从未写过"与"全部关掉"不再撞成同一个状态 —— 旧实现正是撞在一起的那一个。
面板总开关的写法本来就对（`panel-tabs.js` 关闭时逐项 `onToggleGlassChild(id, false)`），
缺的只是"存得住"。

**判据（第 ⑩ 组，6 条）**：全新会话下能力表非空且等于 DEFAULTS；每个已声明 (面,参数) 都可达；
脏存档（三键皆 `{}`）也必须取出完整能力表；两张状态表取各自默认；显式 `false` 存得住；
外加一条**负对照**：把缺陷实现（丢 `def` + 只收 `true`）原地复刻一遍，它必须在同一条判据下变红
—— 这是判据的"灵敏度证明"，否则上面几条可能只是恒真。

金夹具**按意图重生成**（不是再抄一次输出），并带安全阀：除这三个键外任何键漂移即拒绝写入
（`.test-cache/regen-golden-glass.mjs`）。`client` 块只动这三个键 —— 该块本来就是陈旧快照
（夹具 note 原话："client 期望未逐键钉值，只判与 host 共有键一致"），全量重写会把一批与本次
无关的历史陈旧一起写进来，反而掩盖真正的漂移。

**仍未证伪的下一层**：以上把"取值可达性"补齐了，但**样式是否真的命中真实 DOM**
（层叠 / 选择器匹配）依旧只有静态证据。若重测仍无变化，下一层就是它 —— 做法已经想好：
把探针做进插件自身，经 `reportClientDiag` 上报"每个锚点选择器命中几个元素 + 表面算出的
`backdrop-filter`"，仍然不需要用户开 F12（通道见 §4.24）。

### 4.26 第三层：**"不写"不等于"撤销"** —— 关掉独立配置后仍用自己的值

（§4.25 修好后用户实测："现在大部分组件接线了，但大部分组件在配置项关闭时没有如预期接受全局配置，
而是保留自己的配置"。）

**机制**：按面变量是**只写不撤**的。`applyEffects` 里那 6 个**条件写**的变量
（设置窗口 / 左侧栏 / 浮层 × 模糊+透明度）都长这样：

```js
if (swAlphaOn && glassOverrideOn("settingsWindow", "blur")) {
  s.setProperty("--we-settings-window-blur", …);
}                     // ← 没有 else
```

而这一面的 CSS 走的是内层全局兜底：`var(--we-settings-window-blur, var(--we-blur, 16px))`。
**`var(--x, 兜底)` 只在 `--x` 未定义时才取兜底** —— 变量一旦写到 `document.body.style` 上，
它就**一直是已定义**的。于是"关掉独立配置"若只是**跳过写入**，上一档留下的旧值继续被取到
⇒ 该面继续用自己的配置。**缺的是 `else s.removeProperty(...)`，不是缺一段回退样式。**

对话栏那一族（`--we-chat-*`）**不受影响**：它是**无条件写**的，值本身经 `glassValue` 解析，
关掉独立配置时当场读全局 —— 所以它本来就"接受全局配置"。这与用户"**大部分**组件…"的观察一致：
出问题的是条件写的那三面，不是全部。

**修复（`src/effects.js`，3 处）**：每个条件写出的按面变量都补上 `else removeProperty`；
左侧栏与浮层那两处还多一层门控（`leftSidebarGlass && glassIndependentOn(...)`、
`floatersGlassOn && glassIndependentOn(...)`），**外层那一档也必须撤** —— 否则关掉
「左侧栏覆盖」或子项总开关之后，旧值同样留在 body 上。

**判据（第 ⑪ 组，4 条）**：① applyEffects 条件写出的每个按面变量，同一函数里都要有
`removeProperty`；② 值为字面量 `"on"` 的布尔门控属性同理；③ 负对照（删掉任一 else 即变红）；
④ "排除理由的钉子"—— 钉住 `--we-chat-*` 为什么无需撤除，免得将来有人把它改成条件写、
而这条排除就变成真的漏洞。

⚠️ 本组第一版把范围写成"所有 `data-we-*` 属性"，当场把 `data-we-adapter`
（值是 `adapterCaps().target`，**没有"关"态**的钩子）误报成"只挂不摘"。收窄的是**判据范围**
（限定为"被设为字面量 `"on"` 的布尔门控"），不是把失败改成通过 —— 这条区别要留住。

**为什么 ⑨ 组也抓不到它**：⑨ 组查的是 `clearEffects`（**卸载路径**）的对称性 ——
它保证"插件卸掉后不留残留"，但管不到"**运行中切开关**"这条路径。两条路径必须分开判。

**统计一下这个功能暴露出来的层数**（每一层的守卫都是"上一个缺陷的补丁"，值得记住）：
① 部署事实 —— 中间态构建被运行中的 app 取走（§4.24，TDZ）；
② 取值可达性 —— 默认值死代码 ⇒ 能力表恒空（§4.25）；
③ 状态迁移 —— 只写不撤 ⇒ 关不掉（本节）。
守卫的失效方式每次都不一样（形态判据 / 从输出生成的夹具 / 只管卸载路径），
但根子是同一句：**判据只能证明它被测的那一件事**。

## 5. UI 设计

### 5.1 现状：控件散在两节，且"总开关"与"细节"的从属关系只靠命名暗示

今天与玻璃有关的控件分布在**外观页的两个节**里：

| 所在节 | 控件 |
|---|---|
| 「主题」 | 配色（accent） |
| 「细节」 | 玻璃颜色 · 玻璃透明度 · 玻璃保真度 · 对话栏玻璃保真度 · 雾化 · 边框 |
| 「窗口与侧栏」 | 设置窗口液态玻璃（开关）· 侧栏液态玻璃（开关）· 侧栏模糊 · 侧栏透明度 · 侧栏玻璃颜色 |
| 「输入光标」 | 光标颜色（与玻璃无关，但同属"外观"） |

三个问题：

1. **同一个概念被两节切开** —— "玻璃透明度"在「细节」，"侧栏透明度"在「窗口与侧栏」，
   而它们其实是同一参数在两处的取值。
2. **从属关系无表达** —— 侧栏那三个细节**只在侧栏开关打开时**出现（`sel.sidebarPresent && …`
   以及开关前提），但这件事只写在代码里，用户看不出"它们属于侧栏"。
3. **没有"全局 vs 独立"的位置** —— 用户想让"设置窗口用别的模糊"时无处可点。

### 5.2 目标结构：一个「玻璃」节，两层

三层结构在 §3 已定。具体控件树如下（`[ ]` = 开关，`( )` = 滑杆/色板）：

```
外观
├─ 主题            (配色)
├─ 细节            (边框)                      ← 边框不属于釉层，留在原处
├─ 玻璃                                        ← 新节
│  ├─ 全局玻璃
│  │   (玻璃颜色) (玻璃透明度) (雾化) (对话栏玻璃保真度)
│  ├─ 各面独立控制
│  │   [ 设置窗口 ]  → 展开： [独立控制] (颜色)(透明度)(模糊)(保真度)
│  │   [ 侧栏     ]  → 展开： [独立控制] (颜色)(透明度)(模糊)
│  │   [ 左侧栏   ]  → 展开： [独立控制] (颜色)(透明度)(模糊)
│  │   [ 对话栏内容面 ] → 展开： [独立控制] (保真度)
│  │   [ 浮动提示 ]  → 展开： [独立控制] (颜色)(透明度)(模糊)
│  └─ …（每一行的形态完全一致）
├─ 输入光标        (光标颜色)
└─ 全局字体        …
```

**每一行的形态完全一致**（同一组四件套 + 保真度），学习成本一次。这也是 §3.4 的结论：
四件套在**每个面上都有消费点**，所以简化配置的公共参数集就是完整四件套。

### 5.3 两个开关的从属（§3.1 的落地）

```
[启用玻璃]  ── 关 ⇒ 该面恢复宿主原生外观
              └ 开 ⇒ 才显示下面的 [独立控制]
[独立控制]  ── 关 ⇒ 该面继承「全局玻璃」的值
              └ 开 ⇒ 才显示该面自己的四件套
```

"前者是后者的显示前提"（用户口径）在这里就是两级展开。**乙类（左侧栏覆盖）不进这个系列** ——
它的"关"是**恢复背景**而不是恢复纯色（§2），所以它在「玻璃」节里**单独一行、措辞不同**
（"还原背景"而非"加玻璃"）。

### 5.4 三档配置的关系（用户口径：复杂 vs 简化）

「设置窗口」与「侧栏」今天各有一套**复杂配置**（前者是整窗接管 + 令牌重映射，后者是
四件套 + 内容面子面）。新的"全局 + 每面覆盖"是**简化配置**。两者的关系必须明确，否则会
出现"两个地方都能调同一个值、谁赢"的歧义。

提议的规则（**待裁决**，见 §8-3）：

| | 简化配置（「玻璃」节） | 复杂配置（原有位置） |
|---|---|---|
| 覆盖的参数 | 四件套 + 保真度 | 该面**特有**的东西 —— 例如侧栏的**内容面**（编辑器/终端）另有自己的透明度与底色；设置窗口的令牌重映射范围 |
| 优先关系 | 简化配置**写同一批键** ⇒ **不存在谁覆盖谁**：两处是同一份值的两个入口 | 同上 |
| 显示条件 | 总是显示 | 沿用现有条件（如 `sel.sidebarPresent`） |

**关键设计约束**：「简化配置**写同一批键**」这一点是刻意的 —— 若两处各写一套键，
就又有两份真源（正是本方案要消灭的东西）。所以复杂配置不是"另一套值"，而是
"同一批键在更专业语境下的另一个入口"。

### 5.5 实施代价：控件序是**有夹具钉着的**

新增一个「玻璃」节 + 把玻璃控件从「细节」「窗口与侧栏」搬过去，会**改变控件序**，
而外观页的**节序**与**控件标签序**都被 `test/verify-scene-live.mjs` 的 `MORE_CASES`
逐项钉住（判据是**有序序列相等**，不是集合相等）。已知要同批更新的四处：

| 用例 | 现在的 `want`（节序） | 现在的 `wantLabels` 里的玻璃项 |
|---|---|---|
| 设置页·五节 | `主题 细节 全局字体 输入光标 窗口与侧栏` | `玻璃透明度 · 玻璃保真度 · 对话栏玻璃保真度 · 左侧栏覆盖 · 雾化 · 边框 · 设置窗口液态玻璃` |
| 侧栏档·设置页专属三节不画 | `主题 细节` | 同上（减去设置页专属项） |
| 设置页·字体自定义开 | 同"五节" | 同上（另含字体家族那一长串） |

> 注：`玻璃颜色` 是 `swatchRow`、`配色` 也是 —— `wantLabels` 只收 `SliderRow` / `switchRow`
> 之类带标签的控件，所以上表列的是那批；改动时要按夹具**实际报出的差异**更新，
> 不要照本节的清单抄（清单是设计期的，夹具是权威）。

**这件事本身就是一次"判据站在改动对立面"的正当例子**：夹具钉的是**用户可见的控件集合与次序**，
而这次改动**有意**要改它。所以正确做法是**同批更新夹具**（并把新形态固化下来），
**不是**放宽那条判据 —— 它的"有序相等"正是防"某个控件被悄悄挪走/删掉"的手段。

| 乙类单独一行 | **不依赖**（§2 已定） |

| 复杂配置与简化配置的边界 | 依赖 §8-3 |

## 6. 机器对账（防"新面漏登记"）

最危险的漂移是：**新增一个玻璃面，却没人给它登记独立配置** ⇒ 它静默继承全局（或静默读私有值），
而没有任何判据知道。P0 要建的守卫判据草案：

- **枚举面**：从产物 / 源码枚举所有真正画 `backdrop-filter` 或读釉层令牌的位置，按选择器归类。
  （先例：`test/verify-body-caps.mjs` 从磁盘枚举 `req.on('data')` 站点；
  `test/verify-route-families.mjs` 复用生成器的 `buildIndex()` 口径。）
- **每面必须在登记表里**，否则红。
- **`override` 为假的面**：其 CSS 必须消费**全局**变量。
- **`override` 为真的面**：其 CSS 必须消费**该面私有**变量（防"开了开关但没接线"）。
- **保真度一致性**（§3.2）：同一面内，釉色系数与下限覆盖度必须来自同一个保真度值。
- 配**负对照** + **覆盖面地板**，沿用本仓既有手法。

### 10.3 两个实测现象 = 同一个根因

用户实测（本次）：**「子 UI 玻璃」关闭时，全局「玻璃透明度」完全失效；「雾化」对右侧栏无效。**

根因（`lib/settings-schema.js` + `src/effects.js`）：

```js
GLASS_INDEPENDENT_DEFAULTS_ON = { sidebar: true, sidebarContent: true };   // ← 默认「独立」
glassValue("sidebar", "blur",         norm(selection.sidebarBlur, 200),  norm(selection.blur, 60))
glassValue("sidebar", "transparency", norm(selection.sidebarAlpha, 200), norm(selection.glassAlpha, 60))
```

`glassValue` 在"独立"为真时**读自己的键**；侧栏默认就是独立 ⇒ **全局「雾化」/「玻璃透明度」/
「玻璃颜色」永远到不了右侧栏**。用户 `config.json` 的实测值把两个症状量化了：

```
sidebarGlass: true   sidebarBlur: 0    sidebarAlpha: 192     ← 右侧栏恒用这两个
blur: 0              glassAlpha: 60                          ← 全局这两个滑杆动了没人读
```

而「子 UI 玻璃」一关，对话栏 / 设置窗口 / 浮层全部回原生 ⇒ **剩下唯一还在吃玻璃的就是右侧栏**
⇒ 两个全局滑杆看起来"完全失效"。两句话是**同一件事的两种说法**。

⚠️ **一句必须记下的因果**：§4.25 那处修复**才让这个默认值第一次生效**。修之前 `glassIndependent`
恒为 `{}` ⇒ 侧栏其实在跟全局；修好之后"既有面默认独立"被唤醒。**所以这不是修坏了，而是把一个
长期沉睡的默认值暴露成了可见行为** —— 而它与 §3 的目标架构（"全局的玻璃使用同一套配置语义"）
**直接冲突**。

### 10.4 六条结构性缺陷（为什么这是重构而不是补丁）

1. **两条解析路径**：JS 写值 + CSS 62 处内层兜底。同一个"取谁的值"有两处实现 ⇒
   §4.26 那类「不写 ≠ 撤销」会**在结构上反复出现**（内层兜底让"缺省"与"撤销"不可区分）。
2. **三个键的三态耦合**：`glassChildren`（要不要玻璃）× `glassIndependent`（用户开关）×
   `glassOverrides`（能力表），三处默认值互相矛盾，任一处不一致都是**静默 no-op**。
   更根本：**"能力"应当由"CSS 真的读了这个变量"决定**；现在是手抄一张表，两者可以不一致
   —— §4.25 就是那张表恒空。
3. **不存在"全局玻璃面"**：`--we-glass-alpha` 有 54 处读取，但**可见**的消费者都在按面门控后
   （settings-window 2 条 / left-sidebar 2 条），其余是宿主令牌重映射。子项全关时全局参数
   **没有归属面** —— "全局配置"其实只是"各面的默认值来源"。
4. **量纲不统一** ⇒ "继承"是一次**有损换算**（`norm` / `denorm`），不可往返、不可比较。
5. **"关"的语义与可读性契约纠缠**：令牌层在 `body[data-we-wallpaper]` 下**无条件**生效，且被
   `verify-readability` F1c/F2a 与 `verify-softrender` E2 的字面量锁死 ⇒
   「全关 = 全部原生不透明纯色」**不可能字面成立**。"关"必须**逐面声明它到底关掉什么**。
6. **门控靠字符串约定**：8 个属性挂上百处选择器，守卫只能用正则覆盖率近似（"6/6"），
   漏一处就是"关了还剩一点玻璃味"（浏览器里才看得见）。

### 10.5 目标架构

**核心一句：一次解析、一次写入、CSS 零兜底。**

- **CSS 只消费 `--we-<面>-<参数>`，不再有内层兜底**。"关"写成注册表声明的**原生值**（不是"不写"）
  ⇒ 写入者恒等于唯一来源，「不写 ≠ 撤销」这一类**在结构上不可能发生**。
- **单一注册表 `GLASS_SURFACES`**（把现有 `GLASS_CHILDREN` 升级）：每面声明
  `id / 标签 / DOM 锚点 / 门控属性 / 参数[{变量名, 刻度, 默认}] / "关"的语义 / 默认{enabled:true, mode:'inherit'}`。
  **schema 键、CSS 变量、面板行、守卫全部由它生成**（先例：`childGlassKey()` 生成键名）。
- **三键收成两态**：`enabled` + `mode('inherit'|'custom')`；**删掉 `glassOverrides`** ——
  能力改由"CSP 真的读了这个变量"的**双向对账**保证，不再手抄。
- **量纲统一到规范刻度**（存储 0–60 / 0–100），各面的**显示曲线**留在 UI 层 ⇒
  "继承"退化成一次赋值，可往返、可比较。
- **默认全部 `inherit`** ⇒ 全局参数真正全局（= §8 已裁决的"侧栏观感一次语义迁移"）。
- **面板由注册表生成**（i18n 键派生），消灭手抄表。
- **判据从"形态"升级为"语义"**：`面 × 参数 × (enabled, mode) → 期望写入值` 的**执行型**表；
  另加三条双向对账：**CSS 零兜底** / **每个变量恰有一个写入者** / **每条读该面变量的规则都必须带该面门控**。
- **迁移：加 `settingsVersion`**。⚠️ **这里推翻 §7.1 当时的判断**：那时的结论是"参数值语义化之后
  不存在新旧两种值语义，所以不需要版本标记"。但本节方案**改变了存储形状与量纲**
  （侧栏 0–200 → 0–60、三键 → 两态）⇒ **这次是真的有两套值语义**，版本标记有了非它有不可的消费者。
  **推翻的是前提，不是纪律**：§7.1 那句"没有消费者的死字段不加"依然成立 —— 现在它有消费者了。

### 10.13 模块边界：把玻璃管线单开文件（回应"是否该拆"）

### 10.17 R3b 第四步实施记录：**形状收口**（三键 → 两键，`glassIndependent` → `glassMode`）

R3 的目标形态"**每个面两态**（enabled + mode）"到这里才真正成立。改了三件事：

**① `glassIndependent`（boolMap）→ `glassMode`（modeMap `'inherit' | 'custom'`）**
- 新增 `readModeMap`（与 `readBoolMap` 同一套纪律：缺省键取 `def`、显式值保留、**非法取值一律忽略**）。

- `glassValue(面, 参数, 自己, 全局)` 变成**两态分支**：`glassMode[面] === 'custom' ? 自己 : 全局`。

**② `glassOverrides` 删除**（连同 `kind: 'const'`、DEFAULTS 里那张表、以及 `declaredOverrides()`

**③ `settingsVersion` 2 → 3，迁移加一档**：

|---|---|---|

⇒ 迁移的判准不是"旧键名"，而是"**这个值是不是用户的意图**"：残留丢、选择留。

### 10.18 R4 前半实施记录：**死码清理 + 把它变成判据**

**为什么 R4 切两半**：R4 = 量纲统一 + 死码清理。两者性质完全不同 —— 量纲统一**会改用户滑杆的

先做后者（本轮），前者单独一轮。R4 的验收口径（§10.6"变量三方对账里'写而无人读'归零"）

**① 先测量，别照着清单删。** 写了个三方对账探针（写出 / 消费 / 写而无人读），初版报 6 个候选，
逐个人工分类后发现 **2 个是我自己扫描器的假阳性**：

| 候选 | 真相 |
|---|---|
| `--we-caret-color` | **有人读** —— 消费者是 `effects.js` 里那段**注入的补丁样式表**（`<style id="we-caret-patch">` 的 `caret-color: var(--we-caret-color)`）。只扫 `styles.js` 就会给出**假红** |
| `--we-live-fade` | **CSS 自己声明**（`.we-live-iframe.we-live-on { --we-live-fade: 1 }`）—— 我的"声明"正则只认行首，漏了同行带选择器前缀的形态 |
| `--we-host-` | 动态拼名前缀（`setProperty("--we-host-" + k, …)`），字面量在连字符处截断 ⇒ 不是变量名 |

⇒ 教训（与"读取目标过期 ⇒ 假绿"成对的另一面）：**判据的读取面必须覆盖产品真正会注入的全部 CSS**。

**② 删掉的（3 个 + 它们的 `removeProperty`）**：`--we-wallpaper-blur`、`--we-wallpaper-scale`、
`--we-wallpaper-flip`。它们确实是重构留下的中间量 —— 模糊真正落在 `--we-media-filter`（被消费）、
scale+flip 真正落在 `--we-wallpaper-transform`（被消费），两者都逐字节不变。

**③ 一个**推迟**删除的：`--we-glass-color`。** 它没有 CSS 消费者（配方早改读钳制后的
`--we-surface-tint-light/dark`），**但是** `test/compat-harness-pages.mjs` 用
`getComputedStyle(body).getPropertyValue('--we-glass-color')` 把它当**页面观察量**断言
（要求非空 + DSH 的设置窗口 token 与它同源）。那个 harness **不在任何 npm 脚本里**
（要浏览器页面）⇒ 我**无法在此环境验证**改它之后的结局。**先删写入 = 静默破坏一个不可验证的
观察者** ⇒ 保留写入，并在判据里**显式登记**：

```js

```
正确顺序：先把 harness 的观察点改成 `--we-surface-tint-light`，再删这里的写入 + 删这条登记。
配套一条"**登记表不空转**"（登记了却没人写、或其实有 CSS 消费者 ⇒ 必须删登记），
免得豁免变成一个暗洞。

### 10.19 R4 后半实施记录：**量纲统一**（R0–R4 收口）

### 10.21 用户实测 bug：**「玻璃透明度」最多只能拉到 20%**（R4 的漏改）

**症状**（用户实测）：全局「玻璃透明度」拖不过某个上限，再往右就**跳回 20%**。

**根因**：R4 把刻度统一到 0–100 时改了 `KINDS`、改了面板量程，**漏了处理器里手写的四处取值域**
（`src/client.js`）——它们还是旧刻度：

| 处理器 | 手写钳制 | 应该是 |
|---|---|---|
| `onGlassAlpha` | `0, 60` | `0, 100` |
| `onSidebarBlur` | `0, 200` | `0, 60` |
| `onSidebarAlpha` | `0, 200` | `0, 100` |
| `onSidebarContentAlpha` | `0, 80` | `0, 100` |

而**后果比"钳错"更糟**：`clampNum` 不是截断，是**"在范围内取值、否则回落到默认值"**：

```js
function clampNum(v, lo, hi, fallback) { return typeof v === 'number' && v >= lo && v <= hi ? v : fallback; }
```

⇒ 拖过旧上限 60 的那一瞬间取到的是 `fallback = DEFAULTS.glassAlpha = 20` —— 用户看到的正是
"最多只能拉到 20%"（20 就是默认值）。这条判据的**两个前提都错位**才造成它：
一手写的数字会漂，二 `clampNum` 的语义是回落而不是夹紧。

**修法**（不是补数字，而是**去掉第二处真源**）：新增 `schemaRange(key)`（与 `readOne` 的 `num` 档
同源，支持 `min/max` 写成 `CONSTS` 的名字），把 **10 处**手写取值域改成
`clampNum(x, ...schemaRange("<键>"), DEFAULTS.<键>)`（玻璃/侧栏/内容面/壁纸透明度/轮播间隔）。
具名常量那两处（`ROPE_SCALE_MIN/MAX`）**不动**：schema 的 KINDS 引用的就是这两个名字，本来同源。

**让它回不来（两条新判据）**：
1. `verify-client`：凡 `clampNum(…, DEFAULTS.<键>)` 的调用，取值域里**不许出现数字字面量**
   （`...schemaRange(...)` 与具名常量不算违规）。负对照同时喂三种形态：`0, 60` 必须判出、
   `...schemaRange("glassAlpha")` 与 `ROPE_SCALE_MIN, ROPE_SCALE_MAX` 不许判出。
   ⚠️ 判据第一版写错过：修好后的调用源码里只有**三个实参**（`...schemaRange(...)` 在运行期展开成
   两个），按"四个实参"写的正则会漏掉它们 —— 已按"最后一个实参是 `DEFAULTS.<键>`"重切。
2. `verify-client`：面板上「玻璃透明度」的 `max` 必须是 `100`。加上第 ⑦ 组钉住 `KINDS` 本身，
   于是 **KINDS ↔ 面板量程 ↔ 处理器取值域** 三者同源才算闭环（这次事故里前两者对、
   第三者错，任何单点判据都看不见）。

**证据**：`npm run verify:all` **EXIT 0**；`npm run verify:docs` **EXIT 0**（GUARD-MAP 逐字一致）。
⚠️ **这个 bug 在已提交的 `d2ad198` 里**（R4 的漏改），而修复目前落在**未提交**的这一批里 ——
要不要补一次提交（或 amend）由用户定。

### 10.23 收尾（死码清理 + 文档与实况对齐）

**① 删 `readBoolMap`（死种类）**。`glassChildren` 退役后它**没有消费者**了。
删之前把它那条教训**移挂到 `readModeMap` 的头注释**上（那是仍然活着的那条纪律）：

> **`def` 必须从 `readOne` 传进来**。当年布尔映射把 `def` 丢掉 ⇒ 两张默认表成了**死代码**
> （真实会话里恒为 `{}`）⇒ 表现为"控件在、开关滑杆动了没反应"（§4.25 的原始事故）。

顺带删 `case 'boolMap'`、修正文件头与登记表头里对两个已删键（`glassChildren` / `glassOverrides`）的叙述。

**② 删 `CHILD_CN.label`（死数据）+ 4 条 i18n 词条**。`label` 是"每个子面的玻璃开关"的标签，
那个开关随 §10.20 退役 ⇒ 字段没人读。i18n 表因此从 631 条降到 **627 条**（零漏译 / 零孤儿）。

**③ 修好一条"自己也腐烂了"的判据**（本次收尾最值得记的一条）：

第 ⑩ 组的负对照原先这样写 —— `canon(legacyBoolMap(undefined)) !== canon(SCHEMA.DEFAULTS.glassChildren)`。
而 `glassChildren` 已经在 §10.20 被删掉 ⇒ `SCHEMA.DEFAULTS.glassChildren` 是 `undefined`，
`canon(undefined)` 与**任何**对象都不相等 ⇒ 这条负对照**恒真**：它从"有牙"退化成了"摆设"，
而**没有任何东西会告诉你**。已改成对照 `SCHEMA.DEFAULTS.glassMode`，并加一道
"默认表确实非空"的守门（防它退化成 `{}` 之后再次恒真）。

> **这是判据腐烂的第三种形态**，与前两种配成一套：
> · **读取目标过期 ⇒ 假绿**（判据盯着一份已经没有相关代码的文件）；
> · **输入过期 ⇒ 假红**（探针的入参还在用已删的键）；
> · **引用过期 ⇒ 恒真**（负对照里引用了已删的键，比较永远成立）。
> 三种的共同修法都是同一句：**删键时，把所有"提到它"的地方一起过一遍**（判据与探针也算"提到"）。

**④ 清理重构期的临时产物**：`.test-cache/` 里本次重构期的 **197 个**脚本/探针/日志已删
