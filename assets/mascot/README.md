# 吉祥物（拉绳）源资产

本目录归档**「聊天吉祥物」/ 拉绳功能**的原始美术素材。它们是**源资产**，不是运行时载荷：

- 运行时用的是 10 张立绘的 base64 派生版本：**载荷字节住
  [`../rope/`](../rope/README.md)**（`assets/rope/<名>.png`），由
  [`scripts/build-client.mjs`](../../scripts/build-client.mjs) 在构建期注入 `lib/client.js`。
  `src/client.js` 里只剩声明与 `__ROPE_ART_<NAME>__` 占位符（见 `ROPE_IMG_<NAME>` 常量及其注释）。
  ⚠️ 2026-10-13 之前这些字节是**内联在 `src/client.js`** 的 10 条巨型常量；本 README 下文凡提到
  「转 base64 内联 / 替换对应常量」的步骤，载荷落点一律改读 [`../rope/README.md`](../rope/README.md)：
  写 `<名>.png` 到 `assets/rope/`，源码只留占位符，`npm run build` 负责拼回。
- 因此本目录**不进 npm 包**（不在 `package.json` 的 `files` 白名单内），只随仓库源码分发。
- 原本散落在**仓库根目录**（三个 `ChatGPT Image …png` + 一个 hash 名 `.svg`），P0-2 归入此处并
  改成可读名。`git mv` 完成，历史可追。

## 2026-10-11：八只「模型娘」+ 菲比啾比换图

用户提供了 8 个模型各**两张**图（`<名>.png` 与 `<名>_transparent.png`，各 2048×2048）。
**入库的是 `_transparent` 那一版**，判据不是文件名而是**实测 alpha**：

| 版本 | 四角像素 | 透明像素占比 | 结论 |
|---|---|---|---|
| `<名>.png` | 全为 `0,0,0`（纯黑，不透明） | 0.0% | 黑底，**不能**直接内联 |
| `<名>_transparent.png` | 四角透明 | 51.9–57.3% | ★ 背景已抠，**入库** |

> ⚠️ 命名容易反直觉（看目录名以为 `_transparent` 才是带底的那版）。**下次换素材请照这条实测流程走**，
> 不要凭文件名挑。

### 这 9 张的派生参数（可复现）

源图四周有 **19.8–29.8%** 是透明留白 ⇒ 流程是**先裁到 alpha 紧致包围盒，再按面积平均缩放**，
统一**高 384**（与Deepseek_Pro同档），转 base64 内联：

| 形态 | 源（`_transparent`） | 裁边后 | 内联像素 | 显示盒 |
|---|---|---|---|---|
| `claude` | 2048×2048 | 1655×1961 | 324×384 | 64×76 |
| `deepseek` | 2048×2048 | 1700×1978 | 330×384 | 64×74 |
| `gemini` | 2048×2048 | 1526×1977 | 296×384 | 64×83 |
| `gpt` | 2048×2048 | 1641×1972 | 320×384 | 64×77 |
| `glm` | 2048×2048 | 1600×1996 | 308×384 | 64×80 |
| `grok` | 2048×2048 | 1598×1972 | 311×384 | 64×79 |
| `kimi` | 2048×2048 | 1554×1996 | 299×384 | 64×82 |
| `qwen` | 2048×2048 | 1582×1976 | 307×384 | 64×80 |
| `phoebe`（**换图**） | 1254×1254 | 902×1223 | 283×384 | 64×87（原 64×64） |

⚠️ **缩放的三个坑**（第一版脚本踩过第一个）：
1. **必须在预乘 alpha 空间做面积平均**：直接在非预乘空间平均，透明区的黑/白会渗进边缘 ⇒ 描边发灰。
2. **PNG 要用自适应行 filter**（Sub/Up/Average/Paeth 里取绝对值和最小者）：只用 filter 0 会大 30–50%
   —— 这些图是内联进 `client.js` 的，体积直接换加载时间。
3. **编码完要自检不透明像素占比**（应 ≈ 60%）：编码器把 `cand.copy(best)` 写成 `best.copy(cand)`
   时，症状是**每行 filter 数据全 0 ⇒ 全透明 ⇒ 每张只剩 1 KB**，而"体积很小"看起来还像优化得好。

⚠️ **本目录没有归档这 9 张原图**（用户原件在仓库外）：9 张 2048² PNG 合计约 **21 MB**，是现有
`assets/mascot/` 全部内容的 4 倍。派生所需的一切（源尺寸 / 裁边结果 / 目标尺寸 / 显示盒）都在上表里，
按上表 + 上面三条坑即可从原件复现。**若作者希望把原件也归档进仓库，请明说** —— 那是一次
21 MB 的提交，值不值得由作者定，不由我替他决定。

## 2026-10-13：#180 内嵌的那张立绘就是 `glm`（不是新形态）

整合 PR #180 时发现：`factory-default` 预设的 `assets.mascot` 里塞着一张**内嵌立绘**
（`mascot-mv3l8ylw9s9f.webp`，512×512、62,672 B）。它已被**认出就是内置 `glm` 的立绘**：

| 对照（白底 alpha 合成后逐像素，都缩到 308×384） | MAE |
|---|---|
| 那张 webp vs 内置 `glm` | **4.22** |
| 那张 webp vs 内置 `phoebe`（负对照） | 79.21 |
| 内置 `glm` vs 内置 `phoebe`（负对照） | 80.12 |

透明包围盒的宽高比也一致（webp 400×499 = 0.8016，`glm` 308×384 = 0.8021），而它的 alpha 更
"软"（平均 0.4606 vs 0.6051）⇒ 是同一张画的**重采样放大版**。

口径（作者定，2026-10-13）：**不新增形态、不归档重复素材** —— 预设的资产段改为零字节指向
`"glm"`（`values.ropeForm` 同步），那张 512×512 的 webp **不进仓库**（要复原时从 #180 的
`e3a2091` 取：它就在 `lib/glass-presets/factory-default.json` 的 `assets.mascot` 里）。

> ⚠️ 教训（判据没牙）：本次一开始用「非透明包围盒裁剪 + 灰度 48×48 MAE」判定"它与当时 11 只
> 内置都不是同一张画（最小 41.98）"，而**同一算法给出的不同角色之间基线也是 39–52** —— 它根本
> 分不开同画与异画（同画被判成异画）。换成**白底 alpha 合成 + 宽高比对齐**后，同画 4.22 /
> 异画 79–80 一目了然。下次比图先用这条。

## 替换素材时怎么重新生成内联派生版本

1. 把新立绘处理成**透明背景 PNG**（实测四角 alpha=0，别只看文件名）。
2. 按形态缩放到既有目标尺寸（`object-fit: contain` 依赖它与渲染盒同比例）：
   - `whale` → **384×576**，写入 `ROPE_IMG_WHALE`
   - 其余形态 → **高 384**（宽度按各自裁边后的比例），见上表
   - 已除名的 `maid` → **256×283**；它现在**不在 `src/client.js` 里**，而是作为「作者自用」预设
     `lib/glass-presets/factory-author.json` 的 `assets.mascot.data`（键序 `file` → `box` → `data`，
     `box` = `52x57`）
3. 转 base64 data URI 替换对应常量（`maid` 则替换预设里的 `data`），然后 `npm run build` 重建 `lib/client.js`
   （产物不入库；CI 会重建并断言产物与源码逐字节一致）。
4. 新增形态时同步三处：`ROPE_FORMS`（`img` + 显示名 + 基准盒 `w/h`）、
   `lib/settings-schema.js` 的 `ROPE_FORM_VALUES`（**单点真源**，`src/client.js` 只用不声明）、
   以及 `lib/client.js` 的重建。并遵守既有不变量：常量必须在 `readPersisted()` 之前声明（`const` TDZ）。
5. ⚠️ **改了 `lib/settings-schema.js` 要重启 DSH**：它在宿主启动时加载一次，客户端刷新拿不到新的
   校验表（症状：面板里选了新形态、重启前被 sanitize 回默认 `deepseek`）。
